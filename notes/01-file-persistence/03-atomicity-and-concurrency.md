# 原子性、持久性与并发控制

状态：已有正文 · 代码：[atomic-save/main.go](../../experiments/atomic-save/main.go) 的 `SaveData1/2/3`

## 三个不同的问题

| 概念 | 解决什么问题 | 保存示例中的手段 |
| --- | --- | --- |
| 原子性 | 一次操作要么全做，要么全不做，不暴露"做一半"的中间态 | 临时文件 + rename 的路径替换 |
| 持久性 | 已承诺的数据在指定故障模型下能恢复 | 文件与父目录同步，还要满足平台与设备要求 |
| 并发控制 | 多个操作交错时不互相覆盖业务更新 | 保存示例不涉及 |

保存示例讨论的是前两个维度；`SaveData3` 还缺父目录同步，本身不是完整的持久性协议（见 [原子文件替换](05-atomic-file-replacement.md)）。

## 场景 1：rename 替换与完整版本

进程 A、B 各自准备完整内容并保存：

```text
A: 写 path.tmp.111 → fsync → rename(path.tmp.111, path)
B: 写 path.tmp.222 → fsync → rename(path.tmp.222, path)
```

- 随机后缀加 `O_EXCL` 避免临时文件名碰撞后互相覆盖。
- 两次 rename 都成功时，后完成替换的版本成为该路径的内容。
- 在同文件系统 rename 原子替换的前提下，观察者通过路径拿到的是 A 或 B 的**完整**版本，而不是两份内容拼出的混合文件。

这说的是替换时可见的版本，不能据此承诺断电后的恢复状态，也不代表所有损坏情况都已处理。

## 场景 2：lost update（更新丢失）

```text
时刻 1：A 读 path，得到 {x: 1}
时刻 2：B 读 path，得到 {x: 1}
时刻 3：A 改成 {x: 2}，写回
时刻 4：B 改成 {x: 3}，写回   ← 覆盖了 A 的修改
最终：path 是 {x: 3}，A 的更新丢失
```

即使每次保存都是原子且持久的，A 的业务更新仍被 B 覆盖。单次替换的原子性无法协调"读 → 改 → 写回"这一整个业务操作，这需要并发控制。

## 多个进程打开同一个文件

Linux 允许多个进程分别打开同一个普通本地文件。每次独立 open 有各自的偏移和打开状态，但指向同一个文件，不会得到独立的内容副本。（[open](https://www.man7.org/linux/man-pages/man2/open.2.html)）

打开文件不会自动取得独占锁。普通文件的 `flock` 是**协作式**锁：只有遵守锁协议的访问者才受约束。fsync 也不能代替并发控制。（[flock](https://www.man7.org/linux/man-pages/man2/flock.2.html)）

## 数据库如何分层处理并发

1. **进程间**：用文件锁或其他所有权协议，约束谁可以操作数据库文件。
2. **进程内**：用事务、锁或 MVCC 协调访问。

简单的路线是 B+Tree CoW 配合全局写锁（bbolt 即单写者）；PostgreSQL、InnoDB 的 MVCC 是更复杂的对照。不同产品的打开与并发模型各不相同，不能一概而论；pid 文件也不等于锁协议。

处理并发问题时，要先分清缺口属于哪一层：单次保存的原子性与持久性、分页与 B+Tree、CoW 与事务边界，还是进程间的所有权。
