# 长 key：短引用、短分隔键与前缀压缩

状态：部分已整理

## 问题

内部目录保存完整的最小 key，长 key 会让父页装不下（[为什么要限制 key 长度](../03-btree-pages/12-internal-grouping-and-key-limit.md#为什么要限制-key-长度)）。本项目的做法是限制 key 最长 1000 字节。一个自然的想法是：能不能用一个短数字或短字母标识代表长 key，需要时再取回原文？这是否意味着要先有另一个 KV 才能造 KV？

答案是：短引用和短分隔键都是可行的方向，但它们解决的问题不同，也都带来管理成本；显式限制长度同样是成熟数据库的常见取舍。

## 方案一：短引用定位完整 key

目录项保存"部分 key 字节 + 完整长度 + 剩余内容的存储位置 + 孩子页号"。存储位置可以直接是页号与页内偏移，或者一条溢出页链；**它不需要是另一个按 key 搜索的字符串代号**，所以不会陷入"先有 KV 才能造 KV"的循环。

```text
目录项中的 key 存储引用 → 读取原 key 的字节
目录项中的孩子页号     → 沿树下降到孩子
```

比较时先看页内的部分字节；足以判定大小就不必读剩余部分，否则按引用取回再比较。完整长度、结束位置、前缀相同时的长度比较都要有明确规则。

**不变量：比较依据仍是原 key 的比较规则。** 存储地址或任意编号本身不保序：apple… 编号 900、banana… 编号 100，按编号排序就与原 key 顺序相反。普通哈希也不保序且会碰撞，不能替代按原 key 排序的范围路由。

代价：比较可能要访问额外的页；还需要定义引用编码、溢出内容读取与生命周期。空间限制被转换成了额外读取与管理成本。

## 方案二：保存足够路由的短分隔键

若约定查询 key 小于分隔键走左、大于等于走右，非空相邻子树的分隔键只需满足：

```text
max(left) < separator <= min(right)
```

例：左边最大 key 是 apple…，右边最小 key 是 banana…，用 `b` 作分隔键就够了。它不必还原成 banana…，也不必是真实存在的 key，本身就能参与比较。这与任意编号不同：编号只说明"去哪取原文"，分隔键直接说明"大小在哪分界"。叶子里仍保存完整的用户 key。

**失败边界**：分隔键不保证总能截短。两个边界 key 的前 2999 字节相同时，分隔键可能仍然很长；也不能固定截取若干字节就假设范围仍能区分。

这与本项目"minKey 必须等于子树实际最小 key"的契约不同；若采用，路由与更新规则都要重新设计，不能在现有 minKey 上随意截短。

## 相关：公共前缀压缩与显式限制

- **前缀压缩**：多个 key 共享的前缀只存一次，读取时重建完整 key。
- **短分隔键**：内部节点干脆不保存不影响路由的尾部。

两者目的相近但表示和比较规则不同。没有共同前缀时，前缀压缩未必有效。

**限制索引项大小**也是成熟数据库的取舍：能存储大字段，不等于能把同样大的内容完整放进任意索引。

## 工业实现

| 实现 | 行为 | 资料 |
| --- | --- | --- |
| SQLite | 索引 B-tree 的叶子页与内部页都可以把过大的 key 载荷部分留在本页，其余放入由页号连接的溢出页链 | [Database File Format](https://www.sqlite.org/fileformat.html) |
| WiredTiger | `internal_key_truncate` 丢弃内部 key 中不必要的尾部字节（对自定义 collator 不适用） | [WT_SESSION 配置](https://source.wiredtiger.com/develop/struct_w_t___s_e_s_s_i_o_n.html) |
| WiredTiger | 支持 key 公共前缀压缩，以额外的恢复处理换取较小表示 | [Tuning page size and compression](https://source.wiredtiger.com/develop/tune_page_size_and_comp.html) |
| PostgreSQL | B-tree 索引项不能超过约三分之一页（适用时按 TOAST 压缩后的大小计） | [B-Tree Indexes](https://www.postgresql.org/docs/current/btree.html) |

上面的 apple/banana 与"页号 + 偏移"是原理说明，不是这些产品的具体编码格式。

## 待解决的问题

1. **怎样标识一条记录保存的是引用 key？** 可以考虑显式的编码类型或标志字段区分页内内容与引用；不能用某个用户 key 字节串当标记，因为 key 可以包含任意字节。字段位置、版本兼容、长度解释、引用有效性与损坏处理都要设计。当前页格式没有这个标识。
2. **短分隔键什么时候需要改？** 判断依据是所选路由约定下的分界不变量，而不是每次最小 key 变化都改写，也不能假定它永远不变。分裂、重分配、合并时何时重新选取、怎样通知父层并继续向上传递，需要结合完整的更新协议推演。

相关的问题还有：引用数据的所有权与回收、多个节点能否共享同一份原 key、比较时怎样避免过多随机读取、分隔键变长后父页容量怎么处理。

## 本项目现状

[layout.go](../../btree/layout.go) 的 `getKey` 直接读取页内字节，`leafAppendKV` 编码完整 key，没有引用 key 的标识或解引用流程；`internalEntry.minKey` 的契约仍是子树实际最小 key，没有短分隔键。key 上限 1000 字节在 `internalBuildSplit` 与整树 `put` 入口检查。
