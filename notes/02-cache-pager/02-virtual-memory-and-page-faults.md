# 虚拟地址、页表与按需缺页

状态：已有正文 · 代码：[mmap 基础实验](../../experiments/mmap/step1_mmap_basic/main.go)

## 程序看到的地址不是物理位置

每个进程看到自己的虚拟地址空间。Go 代码访问 `data[100]` 时用的地址（例如 `0x7f8e_3c00_0064`）不直接表示物理 RAM 的位置。

```text
进程的虚拟地址空间                     物理 RAM
┌─────────────────────────┐          ┌───────────────────┐
│ 程序代码段、数据段        │          │ 物理页框 #847261   │
│ 堆                       │   映射   │ 物理页框 #239847   │
│ mmap 映射区              │ ───────→ │ 物理页框 #918273   │
│ 栈                       │          │ ……                │
└─────────────────────────┘          └───────────────────┘
```

地址空间大小、页大小等数值随平台与配置而异。

## MMU、页表与映射记录

MMU 负责把虚拟地址翻译成物理地址；页表由内核管理，记录翻译所需的信息。

```text
虚拟地址 0x7f8e_3c00_0064 ──地址翻译──▶ 物理地址 0x0000_aabb_cc64
```

要区分两类信息：

- **映射记录**：这段虚拟地址来自哪个文件的哪个偏移、有什么权限。
- **页表项**：这个虚拟页当前对应哪个物理页。

| 虚拟范围（示意） | 文件映射来源 | 权限 |
| --- | --- | --- |
| `0x4000_0000_0000` 起的一页 | `/tmp/demo.bin` offset 0 | rw |
| 下一虚拟页 | `/tmp/demo.bin` 下一页 | rw |

上表是入门示意，不是硬件页表项的真实布局。映射管理结构和页表都占用内核内存。`mmap` 建立的是虚拟映射，并不意味着当场为每个数据页建好驻留的页表项。（[Linux Page Tables](https://docs.kernel.org/mm/page_tables.html)）

## 第一次访问可能发生什么

```text
访问 data[100]
    │
    ▼
能否通过当前页表完成这次访问？
    ├─ 能：按映射访问物理内存
    └─ 不能：触发缺页，交给内核
              ├─ 文件页已在缓存：建立映射
              └─ 需要读取文件页：取得数据后建立映射
              ▼
          恢复这次访问
```

访问过的页也可能在内存压力下被回收，之后再访问会再次缺页。程序不必为每次缓存缺失写 `ReadAt`，但等待和错误仍然可能发生。

"映射 1 TB，只在访问某页时才加载"说明了虚拟范围与驻留内存的区别，但不能推出"映射瞬间完成""物理内存零占用""第一次访问必然读磁盘"：内核记录映射本身有成本，文件页也可能早已在页缓存里。页面回收策略因平台而异（对照见 [页缓存与 buffer pool](07-page-cache-versus-buffer-pool.md)）。

## 对 Go slice 的含义

```text
data:
    ptr = 0x4000_0000_0000   # 虚拟地址
    len = 8192              # 映射长度
```

slice 的长度决定 Go 下标的可访问范围；映射与底层文件的状态还决定这次访问能否完成。两者不同，见 [页生命周期与 Pager 错误](06-page-lifetime-and-pager-errors.md)。
