# 笔记 04：虚拟内存 / 页表 / mmap 到底怎么工作

> 笔记 03 讲了 mmap 的用法，这一篇讲它的**机制**——
> 搞懂这个，mmap 不再是玄学，写存储引擎/网络服务时也都用得上。

---

## 1. 关键事实：程序看到的"内存地址"不是真实物理地址

每个进程都有自己的**虚拟地址空间** (virtual address space)，
是个巨大的、空荡荡的地址坐标系（64 位进程 ~256TB）。

```
你的 Go 程序看到的世界：            真实物理 RAM：
┌────────────────────────────┐    ┌───────────────────────┐
│ 虚拟地址空间 (~256TB)        │    │ 一堆 4KB 的物理页框    │
│                            │    │ (机器实际装的 16GB 等) │
│ 程序代码段                  │    │                       │
│ 数据段                      │    │  [物理页 #847261]     │
│ 堆 (heap)                  │    │  [物理页 #239847]     │
│ ...                        │    │  [物理页 #918273]     │
│ mmap 映射区                 │    │  ...                  │
│ ...                        │    │ (任何进程的任何数据)   │
│ 栈 (stack)                 │    │                       │
└────────────────────────────┘    └───────────────────────┘
```

→ 当代码写 `data[100]`，CPU 看到一个虚拟地址（如 `0x7f8e_3c00_0064`），
但这**不是**物理 RAM 上的位置。

---

## 2. MMU + 页表：虚拟 → 物理的翻译

CPU 内置一个硬件单元 **MMU (Memory Management Unit)**，
每次访问内存都做一次翻译：

```
虚拟地址 0x7f8e_3c00_0064
         │
         ▼
   查"页表" (page table)
         │
         ▼
物理地址 0x0000_aabb_cc64  ← 真实 RAM 的位置
```

**页表是内核为每个进程维护的一张表**（简化）：

```
┌──────────────────┬────────────────────────────┬───────┐
│ 虚拟页起始        │ 对应的物理页 / 文件来源     │ 权限   │
├──────────────────┼────────────────────────────┼───────┤
│ 0x7f8e_3c00_0000 │ 物理页 #5829               │ rw    │  堆
│ 0x4000_0000_0000 │ 文件 /tmp/demo.bin off 0   │ rw    │  ← mmap!
│ 0x4000_0000_1000 │ 文件 /tmp/demo.bin off 4096│ rw    │  ← mmap!
└──────────────────┴────────────────────────────┴───────┘
```

→ **mmap 干的事就是在页表里加几行记录**：
> 「虚拟地址 X 开始的 N 字节，对应的不是物理 RAM 块，而是某文件的某段」

---

## 3. "映射存在哪里？"

> **它就是内核内存里一张查找表（页表）里的几行记录**。
> 不在 RAM、不在磁盘、不在文件——就是一组**翻译规则**。

这就是为什么 `mmap()` 本身**不读磁盘**，
也是为什么映射 1TB 文件**瞬间完成**（只加几行表项）。

---

## 4. 访问数据时发生什么？(Demand Paging)

```
访问 data[100]（假设 data 是 mmap 出来的 slice）:

 1. CPU 拿虚拟地址 0x4000_0000_0064
        │
        ▼
 2. MMU 查页表 → 文件 /tmp/demo.bin 的 offset 100
        │
        ▼
 3. 这个文件页在物理 RAM 里吗？
        │
   ┌────┴────┐
   ▼         ▼
  在        不在
   │         │
   │         ▼
   │       触发"缺页中断" (page fault)
   │         │
   │         ▼
   │       内核接管：
   │       - 从磁盘读这 4KB 进一块空闲物理页
   │       - 更新页表，把这一行指向新物理页
   │       - 让 CPU 重试访问
   │         │
   ▼         ▼
 4. 翻译成物理地址，读出字节，返回
    (纯硬件操作，几纳秒)
```

**关键点**：
- `mmap()` 本身只改页表，不读磁盘 → 即使映射 1TB 也瞬间完成
- 真正读磁盘发生在**第一次访问那一页**（lazy loading）
- 之后访问那页就纯内存，几纳秒
- 内核用 LRU 把不常用的物理页"踢"出去回收 RAM，
  下次访问再 page fault 读回来——**对你的代码完全透明**

---

## 5. 写操作 + Dirty Page

`data[0] = 'X'` 发生什么：

1. MMU 翻译虚拟地址 → 物理页
2. 改物理页里那一字节
3. **MMU 在页表里标这一页为 "dirty"**
4. 内核后台进程 (Linux: pdflush / kernel writeback) 周期性扫描 dirty 页，写回文件
5. `fsync()` / `msync()` = 立刻强制扫一遍、写完才返回

→ 这就是为什么"hexdump 立刻看到 X"但"断电就丢"：
- **立刻看到**：page cache 里的物理页已经改了，其他进程读时也从这取
- **断电丢**：内核还没来得及写回磁盘

---

## 6. MAP_SHARED vs MAP_PRIVATE 的真正区别

| 模式         | 页表项指向                             | 写操作                                              |
| ------------ | -------------------------------------- | --------------------------------------------------- |
| `MAP_SHARED` | 直接指向 page cache 中的物理页         | 改 → 标 dirty → 异步写回文件，其他进程也看得到      |
| `MAP_PRIVATE`| 初始指向 page cache 中的物理页（共享） | 首次写时触发 **COW**：复制一份私有物理页，改私有副本，**永不写回文件** |

COW = **copy-on-write**。读的时候大家共享同一份物理页（省 RAM），
某进程一旦写入才复制——所以 PRIVATE 模式很轻量，但写不持久化。

→ 这就是为什么实验 B 里 `MAP_PRIVATE` 改了 `data[0]`，
hexdump 看到的还是原内容：内核给你做了 COW，改的是私有副本。

## 7. 用 step1 的例子完整画一遍

代码运行后：

```
进程内 (Go 视角)：
  data 是一个 slice，header 里：
    ptr = 0x4000_0000_0000    ← 虚拟地址
    len = 8192

内核里 (页表)：
  这个进程的页表多了 2 行：
    虚拟 0x4000_0000_0000 → 文件 demo.bin offset    0~4095
    虚拟 0x4000_0000_1000 → 文件 demo.bin offset 4096~8191
                                            ↑ 但文件只有 64 字节
                                            ↑ 这一页其实没数据

磁盘上：
  /tmp/demo.bin  共 64 字节  "HELLO MMAP!..."

物理 RAM：
  (还没访问过 → 物理上没分配任何东西)

────────────────────

第一次 data[0]：
  → page fault → 内核读 4KB 进物理页 #X → 页表更新
  → 读出 'H'

data[0] = 'X'：
  → 物理页 #X 那一字节改 'X' → 页表标 dirty

data[5000] = 0xff (实验 C)：
  → 虚拟地址在"映射内"但"文件外"
  → Linux：SIGBUS
  → macOS XNU：常常默默给你一块"幻影内存"（行为不一致）
```

---

## 8. 一句话总结

> **mmap 不复制任何数据**。它在内核页表里加几行规则，告诉 CPU：
> 「以后看到这段虚拟地址，按这个规则去找数据。」
> 数据在**第一次访问**时被加载到物理 RAM，改后标脏，
> 由内核或 fsync 写回文件。

---

## 9. 为什么这套机制对数据库重要

1. **零拷贝**：B+Tree 直接读写 mmap 的 slice = 直接读写 page cache，不经任何用户态 buffer
2. **自动缓存**：哪些页留在 RAM 由内核 LRU 决定，省了自己写 buffer pool
3. **统一编程模型**：磁盘上的数据用普通 slice 索引访问，代码极简
4. **代价**：错误是信号不是 error；fault 难调试；文件 grow 要 remap（→ 笔记 [[05-...]]）

主流用 mmap 的数据库：SQLite (默认模式之一)、LMDB、BoltDB。
不用 mmap 的：PostgreSQL、MySQL InnoDB（自己实现 buffer pool，灵活性更高）。
