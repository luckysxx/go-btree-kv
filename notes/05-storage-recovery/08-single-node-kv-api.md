## 嵌入式引擎

本引擎是嵌入式的：它是一个库，与调用者在同一个进程里，读写是函数调用，数据是磁盘上的一个文件；没有服务器进程、端口与连接。之后的分布式阶段，每个 Raft 节点进程是外层的服务器，引擎嵌在其中。

嵌入式与客户端/服务器两种形态的比较、存储引擎层与嵌入式数据库的关系，见通用笔记 [[_knowledge/数据库/04-数据库的形态与分层|数据库的形态与分层]]。

## 并发加在哪一层

| 层 | 是否需要锁 | 原因 |
| --- | --- | --- |
| 树算法 | 不需要 | 已提交的页永不修改（CoW）；每个事务的树归该事务所有，写事务的 dirty 页对他人不可见 |
| 事务 | 不需要 | 约定一个事务只由一个 goroutine 使用 |
| db | 需要 | 只允许一个写事务；内存 meta 被开始事务读取、被提交发布；读者登记表被读事务修改、被写事务读取 |
| Pager | 需要 | 扩容向映射列表追加 chunk 时，读事务正用它定位页 |

与"一把大锁包住全部读写"的内存 KV 相比，这里的目标是读者之间、读者与写者之间互不等待：读事务可能持续很久（扫描全表），若持锁则写者一直阻塞，CoW 换来的"读者不阻塞写者"就失去了。因此锁只保护很小的一块共享状态，树本身不加锁。

## 共享状态与两把锁

| 状态 | 读 | 写 | 由谁保护 |
| --- | --- | --- | --- |
| 内存中的已提交 meta | 事务开始时复制 | 写事务提交时发布 | 状态锁 |
| 读者登记表 | 写事务开始时（决定放出哪些待回收页） | 读事务开始与结束时 | 状态锁 |
| 空闲清单、待回收表、失败状态 | 只有写事务 | 只有写事务 | 写者锁 |

- **写者锁**（互斥锁）：从写事务开始持有到提交或回滚。写事务从开始时的根出发；两个写事务若交错进行，会从同一个根各自得到一个新根，后提交者整个覆盖先提交者。
- **状态锁**（互斥锁）：每次只持有几行代码的时间。不需要读写锁：读事务开始时要登记自己，本身就是写操作。

**为什么是两把而不是一把。** 两者保护的东西不同，被持有的时间也相差几个数量级：写者锁覆盖整个写事务（含两次 fsync，以毫秒计），只在写事务之间争抢；状态锁每次不到一微秒，读事务与写事务都要拿。若合为一把并由写事务全程持有，每个读事务开始时都要等当前写事务做完，读者不等写者的好处就没有了。

**哪些数据需要锁。** 按有没有第二个 goroutine 能同时访问来分：

| 数据 | 例子 | 需要 |
| --- | --- | --- |
| 事务私有 | dirty 页、meta 副本、空闲清单副本、释放列表 | 不需要 |
| 只在写者之间共享 | 空闲清单、待回收表、失败状态 | 写者锁已足够：同一时刻只有一个写者 |
| 读者与写者共享 | 已提交的 meta、读者登记表 | 状态锁 |

### 加锁顺序

写事务会同时持有多把锁，所以要固定顺序：**写者锁 → 关闭用的读写锁 → 状态锁**。读事务只拿后两者；没有任何地方先拿状态锁再去拿写者锁。假如读事务在持有状态锁时去拿写者锁，而某个写事务正持有写者锁、等待状态锁，两边就互相等待。

由此得出两种会死锁的用法：在写事务的回调里再开写事务（写者锁不可重入）；在持有事务的 goroutine 里调用关闭。

粒度的划分、加锁顺序为什么能防止死锁，见通用笔记 [[_knowledge/go/05-锁、Once与条件变量|锁、Once 与条件变量]] 的"多把锁：粒度与加锁顺序"。

### 复制 meta 与登记必须是一个整体

读事务开始时要做两件事：复制 meta、登记自己的版本号。两步之间若插入写事务，会过早重用页：

```
读事务：复制 meta（版本 5），尚未登记，被切走
写事务 6：开始、提交，释放若干页 → pending[6]
写事务 7：开始，发现没有读者 → 放出 pending[6] 并重用这些页
读事务：登记版本 5，开始读 → 读到被事务 7 覆盖的页
```

做法：复制与登记在同一次持锁内完成；写事务开始时"读取登记表并放出待回收页"、提交时"发布 meta"也在这把锁下。于是写事务对登记表的观察要么在读事务登记之前、要么在之后，不会落在中间。

另一种思路是先登记一个占位（表示"暂时不要放出任何页"），复制 meta 后再改为真实版本号。可行，但步骤更多；临界区只有几行时直接加锁更简单。

## 映射列表：写时复制加原子切换

Pager 把文件按固定大小分段映射，映射列表的第 i 项是第 i 段对应的内存（见 [分段映射与三个范围](../02-cache-pager/05-chunked-mmap-and-pager-ranges.md)）。写者扩容时向列表追加一段，可能更换列表的底层数组；读者同时读取列表，构成数据竞争。

用读写锁可以解决，但每次读页都要加锁。利用"已映射的段从不改变，变化只有末尾多一段"，可以让读者不加锁：

```
写者扩容：复制列表 → 在副本末尾追加新段 → 用原子指针把"当前列表"换成副本
读者读页：用原子指针取出当前列表 → 在其中定位
```

读者取到的无论是旧列表还是新列表都是完整的，旧列表中的每一段依然有效。这与 CoW 树是同一思路：不改别人正在看的东西，另做一份再原子切换（通用的写法见 [[_knowledge/go/05-锁、Once与条件变量|锁、Once 与条件变量]] 的"原子操作与不可变快照"）。文件长度同样用原子变量；发布顺序是先换列表、后更新长度，读者则先读长度、后取列表，这样读到新长度时一定能取到包含新段的列表。

## 关闭

关闭会解除映射，仍在进行的事务手中的页切片随即失效。做法是让关闭**等待**所有事务结束：每个事务从开始到结束持有一把读写锁的读锁，关闭时获取写锁，自然等到全部事务结束；另设"已关闭"标记，之后新开事务直接报错。

这把读写锁的"读锁"表示"正在使用数据库"，"写锁"表示"要关闭"，与数据的读写无关：写事务同样持读锁。它同时完成两件事：关闭等待所有已开始的事务；关闭开始等待后，新来的事务被挡住，待关闭完成后看到标记并返回错误。

这种"读写锁做闸门"的写法，以及它与 WaitGroup、channel 的比较，见 [[_knowledge/go/05-锁、Once与条件变量|锁、Once 与条件变量]] 的"用读写锁做闸门"。

代价：读事务若忘记结束，关闭会一直等待。在已经开着事务的 goroutine 里再开事务也要小心：有关闭在等待时，新的读锁会排在它后面，而它又在等这个 goroutine 结束已有的事务，形成死锁。

## 对外接口

- **两层**：`Get`、`Put`、`Delete`、`Scan` 各自是一个完整的事务；`Update(fn)`、`View(fn)` 把多个操作放进同一个事务。前者是后者的包装。
- **value 的归属**：单次操作的 `Get` 返回副本，调用者可以任意使用与修改。事务内的 `Get` 与 `Scan` 的回调返回借用的切片，只在事务或回调期间有效，需要保留时由调用者复制。借用省去一次分配与复制，但"事务结束后继续使用"是这类接口最常见的误用。
- **范围扫描**：`Scan(start, end, fn)` 遍历左闭右开区间，回调返回错误即停止，比直接暴露游标简单。

## 工业对照：bbolt

`DB` 中 `rwlock`（只允许一个写者，对应写者锁）、`metalock`（保护 meta 的读取与发布，对应状态锁）、`mmaplock`（读事务持读锁；重新映射与关闭需写锁，等待所有读事务结束）。`beginTx` 先在 `metalock` 下复制 meta，再持 `mmaplock` 读锁，并把自己的事务号登记到 freelist。bbolt 整体重新映射，所以扩容也要等读事务结束；分段映射不移动旧段，只有关闭需要等待。bbolt 的全部接口返回借用的切片，仅在事务期间有效。

## 与 Raft 的关系

状态机按日志顺序逐条 apply，天然是单写者，单写者引擎足够；需要并发的主要是读。

## LSM 中的对应

多个写者可以并发：写入是向支持并发插入的 memtable（跳表）插入，WAL 由 group commit 将多个写者的记录合并为一次 fsync——LSM 写吞吐高的原因之一（概念见 [B+Tree 与 LSM](../06-storage-comparisons/03-btree-and-lsm.md)）。读者看到一致版本的方式与这里相同：取得当前 Version 的引用（对应复制 meta 并登记），期间它引用的文件不会被删除。

## 验证

两类并发错误用不同的手段（一般性的说明见 [[_knowledge/go/05-锁、Once与条件变量|锁、Once 与条件变量]] 中竞争检测的范围）：

- **数据竞争**：在竞争检测下运行压力测试。多个读者反复开读事务、扫描全表，一个写者每轮改写全部记录；每个读者看到的必须是某一轮的完整版本，轮次不倒退，同一事务内两次扫描结果相同。缺少任何一处状态锁都会被报告。
- **"复制 meta"与"登记"被分成两次持锁**：没有数据竞争，压力测试也极难撞上。测试在两步之间放一个钩子，让另一个 goroutine 在此处连续提交写事务。两步在同一次持锁内时，写事务被挡在锁外，钩子超时返回；否则写事务全部完成并重用了读者的页，读者随后读到残缺的快照。
