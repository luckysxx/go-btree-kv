# 文件格式与元数据校验

状态：部分已整理 · 代码：[db.go](../../btree/db.go) 的 `metaSlotFor`、`metaChecksum`、`encodeMeta`、`decodeMeta`、`pickMeta`、`openDB`；[tx.go](../../btree/tx.go) 的 `begin`（txid 递增）

## 元信息从哪里开始找

重启时需要找到根页。回答"根页号存在元信息里"之后，还要回答"元信息在哪里"。必须有一个代码直接知道的稳定入口，否则就会陷入"元信息的元信息"的无限递归。

本项目约定 meta 在页 0，即文件 offset 0；打开时先读它。**位置约定写在代码里，元信息的内容存在文件里，内容仍然可能损坏。** meta 的字段见 [树与 Pager 接入](02-tree-pager-integration.md#meta-字段)。

其他系统也都有这样一个可定位的入口，例如 ext4 的 superblock、SQLite 的 database header、PostgreSQL 的 `pg_control`，但它们的具体位置和布局各不相同，并不都是"数据库文件的第一页"。文件系统里也是同样的道理：应用通过已知路径访问文件，文件系统又要靠自己的约定找到自身的元数据——入口总是由更低一层约定。

落盘后发布新版本，就是改写这个 meta（例如双 meta 页加校验和），见 [发布到磁盘上的条件](../04-btree-tree/04-root-split-and-publication.md#发布到磁盘上的条件)。

## 撕裂写

磁盘不保证一次 4 KiB 写入是原子的。写 meta 时断电，页可能新旧字节混杂或含垃圾（torn write）；通常只有单个扇区（512 B 或 4 KiB，视设备）的写入可近似看作原子，且并非所有设备都可靠。只有一份 meta 并原地覆盖时，撕裂意味着要么打不开，要么带着错误的根与高水位继续运行，尽管磁盘上的旧树完好。

## 校验和：发现 meta 坏了

meta 中存一个校验和，覆盖除它自身以外的**全部字段**；读出时重算，不一致即判定损坏。

- **magic 不够**：撕裂可能恰好保留开头的 magic，而后面的根、高水位是乱的。magic 只回答"是不是本数据库的文件"，不回答"内容是否完整"。
- **覆盖范围**：漏掉任何字段，该字段损坏就发现不了。
- **不需要密码学哈希**：防的是意外（撕裂、位翻转），不是恶意伪造。bbolt 用 FNV-64a，LevelDB/RocksDB 用 CRC32C（有硬件指令）。64 位校验和偶然吻合的概率约 2⁻⁶⁴，可忽略。
- **另一种做法**：InnoDB 数据页在页头存 LSN、页尾存 LSN 的低 32 位，页从前往后写，撕裂时二者不一致；这依赖写入顺序的假设，所以 InnoDB 另有页校验和。

校验顺序：先 magic（是不是本库文件），再 version（版本不同则布局可能不同，无法计算校验和），再校验和，最后检查字段取值范围。

## 双 meta：永远不原地覆盖唯一的入口

要守住的不变量：**任意时刻，磁盘上至少有一份完整的 meta，且它指向一棵完整的树。**

做法：两个固定槽位（页 0、页 1）轮流写，每次写**较旧**的那份。写入时另一份一定是上一次成功提交的版本；这次写坏就退回上一版，而这次提交从未向调用者报告成功，不会丢掉已确认的数据。

两份都写没有好处：先写 A、sync、再写 B、sync，多一次同步，保证与只写一份相同；若两份同时写、只 sync 一次，一次断电可能把两份都写坏。

### 用事务号决定写哪一份

每份 meta 带递增的事务号 txid，写入槽位 `txid % 2`。写事务开始时 txid = 已提交 txid + 1，它 % 2 必然落在已提交那份**之外**的槽位。meta 在错误的槽位（`txid % 2` 不等于所在页号）也判为无效，这能发现写错位置的 meta。

这条规则成立依赖一个不变量：**内存中的已提交 meta 等于磁盘上最新的有效 meta。**

| 情形 | 磁盘上的 meta 槽位 | 内存 meta | 不变量 |
| --- | --- | --- | --- |
| 回滚、只读事务 | 未写 | 不变 | 保持；下个事务仍用同一 txid，写同一槽位 |
| 写数据页或第一次 sync 失败 | 未写 | 不变 | 保持；该 txid 从未发布，重用无害 |
| 成功提交 | 新槽位持久为新版本 | 第二次 sync 后更新 | 保持 |
| 写 meta 或第二次 sync 失败 | 新槽位可能是新、撕裂或旧，无法确定 | 不变 | **可能被打破** → 进入失败状态，禁止写事务 |
| 失败后重开、任意时刻崩溃后重开 | 选最新的有效一份 | 取它 | 由打开过程重新建立 |

打破不变量后若照常继续，下一个事务会再次使用同一 txid、写同一槽位，并从旧高水位分配页号，覆盖那份可能已生效的新 meta 所引用的页；磁盘上还可能出现两个 txid 相同、内容不同的版本，"选 txid 大者"不再可靠。因此写 meta 之后的失败只能关闭重开（见 [提交顺序与同步](04-commit-order-and-sync.md)），这是双 meta 正确性的前提。

### 打开时选哪一份

| 页 0 | 页 1 | 选择 |
| --- | --- | --- |
| 有效 | 有效 | txid 较大者 |
| 有效 | 无效 | 页 0 |
| 无效 | 有效 | 页 1 |
| 无效 | 无效 | 拒绝打开：magic 都不对是"非本库文件"，否则是损坏 |

只信有效的那份是安全的：无效的只可能是正在写、未确认的那次提交，有效的是已确认的版本。

例：

```
提交前：页 1 = {txid 5}（最新）   页 0 = {txid 4}（上一版）
提交 txid 6 → 写页 0（6 % 2 = 0），覆盖 txid 4
  新数据页写入并 sync → 写页 0 时断电，页 0 撕裂
重开：页 0 校验和不符，页 1 有效 → 选 txid 5
      txid 5 的高水位以上的页（txid 6 写过的）视为不存在，下次提交直接覆盖
```

退回上一版要求它用到的页完好。目前从不回收页，自然满足；引入页回收后，可能被退回的版本用到的页不能复用（见 [页回收与读者](07-page-reclamation-and-readers.md)）。

## LSM 中的对应

LSM 解决同一问题，但不用固定槽位轮流写（概念见 [B+Tree 与 LSM](../06-storage-comparisons/03-btree-and-lsm.md)）：

- **MANIFEST 是只追加的日志**，每条记录带 CRC32C。断电最多撕裂最后一条，恢复时读到坏记录即停，之前的记录都有效——与 Raft 日志残尾的处理相同。
- **CURRENT 指向当前 MANIFEST**，切换时写临时文件 → fsync → rename，依赖 rename 的原子性（即 [原子替换](../01-file-persistence/05-atomic-file-replacement.md) 的做法）。
- **SST 的 footer** 含 magic 与格式版本，每个数据块带校验和。

共同原则：**永远不原地覆盖唯一的一份入口**。B+Tree 用固定位置的两份轮流写，LSM 用追加日志加原子 rename。
