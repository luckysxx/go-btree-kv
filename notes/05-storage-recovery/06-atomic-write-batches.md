# 原子写批次

## 批次的原子性从哪里来

一个写事务中的全部 put 与 delete 只修改事务内的树，由**一次** meta 写入统一发布：meta 写好之前都不可见，写好之后同时可见。原子性不需要额外机制，是 CoW 加单一发布点的直接结果。

```go
d.update(func(tx *tx) error {
    tx.put(k1, v1)   // 只进入事务的 dirty 页
    tx.put(k2, v2)
    return nil       // 返回 nil 才提交；返回错误则回滚
})
```

事务内读得到自己的修改（先查 dirty 页），其他事务在提交前看不到。

## 结果与失败语义

| 发生了什么 | 这批修改 | 调用者得到 |
| --- | --- | --- |
| 函数返回错误 | 全部作废，未写任何东西 | 该错误 |
| 写 meta 之前失败 | 全部作废，等于回滚 | 提交的错误；可以重试 |
| 写 meta 之后失败 | 不确定：全部生效或全部未生效，不会只生效一部分 | 失败状态；重开后才能确定 |
| 成功 | 全部生效 | nil |

**返回错误不等于没有生效。** 第三种情况下原子性仍然成立，只是调用者当时无法得知结果（见 [提交顺序与同步](04-commit-order-and-sync.md)）。上层若要重试，必须能容忍"其实已经生效"，例如操作本身幂等，或带去重标识。

## 本引擎的事务提供什么

本引擎处在事务的最底层，即存储引擎的原子写批次：一次 meta 写入提供原子性与持久性；读事务拿住旧根，看到一致的快照；写者只有一个，写事务之间天然串行，不存在写冲突。它不提供多个写事务并发时的隔离，也不涉及跨节点的事务。

事务在各个层次分别指什么、应用代码划定边界与数据库实现保证的分工，见通用笔记 [[_knowledge/数据库/02-事务与并发控制|事务与并发控制]] 的"事务在不同层次"。

## 事务内的过时页

每次 put 都从根到叶子复制一条路径。同一事务中，后一次 put 会把前一次刚生成的页再复制一遍，前一版立即成为垃圾，却仍在事务的 dirty 页中，提交时照样写盘并占用高水位（实测见 [树与 Pager 接入](02-tree-pager-integration.md#已知代价事务内的过时页)）。批量写入本为分摊两次 fsync 的成本，批次越大多写的垃圾页越多。

### 每张页在一个事务里只复制一次

CoW 需要复制，是因为旧页可能有别人在看：读事务持有旧根，或崩溃后要退回旧 meta。事务自己新建的页不存在这些情况：尚未写入文件，没有 meta 指向它们，其他事务看不到。因此：

- **已提交的页**：第一次修改时复制，副本归本事务所有。
- **本事务新建的页**：直接替换，不再复制。

判断一张页是否由本事务新建，只需看它的页号是否在事务的 dirty 页表中。页存储增加一个操作，由树传入"被替换的页号"：

```
replace(oldID, page)：
  oldID 在 dirty 中 → 用新内容替换 dirty[oldID]，页号不变
  否则             → 分配新页号，放入 dirty
```

一张旧页分裂为多张时，第一张复用旧页号，其余分配新页号。"原地"指复用页号，不是修改字节：dirty 中换入的是新的字节切片，旧切片内容不变，此前借出的 value 依然正确。

### 副作用

- **事务内部不再保留旧版本。** 同一事务中的旧根被直接替换。已提交的版本不受影响，其他事务仍看到完整快照。
- **修改后，本事务此前打开的游标失效。** 游标栈中的页号未变而内容已换，继续遍历可能跳过或重复 key；修改之后需重新定位。
- **事务中任一操作中途出错，事务只能回滚。** 可能出现叶子已替换而父页未更新的不一致状态，不能再提交。输入被拒绝的错误除外：key 过长在动手前检查；记录过大在叶子层发现，而页是自底向上替换的，此时尚未替换任何页，事务完好。

只有事务页存储复用页号。内存页存储的替换仍总是分配新页号，保持"每个旧根都是完整旧版本"，树算法的测试不受影响。

### 效果

| 一个事务内的操作 | 逐次路径复制 | 每页只复制一次 |
| --- | --- | --- |
| 10 次 put | 写出 10 页 | 1 页 |
| 100 次 put | 140 页 | 4 页 |
| 1000 次 put | 1969 页 | 33 页，全部可达 |
| 同一条记录改 20 次（树高 2） | 40 页 | 2 页（一条路径） |
| 1000 次 put 后删除 990 条 | 约 3900 页过时 | 32 页过时 |

只做 put 时没有过时页：写出的页数等于新树中由本事务新建的页数。上表最后一行剩下的 32 页是删空后被摘除的页；引入页回收后，被摘除的页若由本事务新建，立即从 dirty 中删除并回到事务的空闲清单，不再写盘（见 [页回收与读者](07-page-reclamation-and-readers.md)），此时写出的页数恒等于新树中由本事务新建的页数。

### 页与节点：两种形态

同一份数据有两种形态：**页**是磁盘上的字节布局，紧凑、可直接写入文件，但不便修改（中间插入一条，其后的记录位置与偏移数组都要重算，因此整页重建）；**节点**是把这些字节解码（反序列化）得到的内存结构，例如一个按 key 有序的记录切片，插入只是切片操作。二者的关系如同 JSON 字节与结构体。

bbolt 的写事务使用节点：第一次修改某页时 `node.read` 把它解码成节点，归事务所有；之后 `node.put` 只修改节点中的切片；提交时 `node.spill` 对改过的节点做分裂、分配页号，并用 `node.write` 各编码一次。读操作不解码，直接在映射的页字节上查找。

两种做法都会解码，区别在于**解码后的结构存在多久**，也就是两次操作之间事务持有的是哪种形态。本项目在一次修改内部也会临时解码：例如 `leafInsertSplit` 把旧页的记录收集成 `[]leafRecord`，加入新记录后立即用 `leafBuild` 编码成新页，这个切片随函数返回而丢弃。读操作则两者都不解码：`leafGet` 直接在页字节上二分，`getKey` 现场计算偏移并返回指向页内的切片。

| | 复用页号（本项目） | 内存节点（bbolt） |
| --- | --- | --- |
| 两次操作之间事务持有 | 已编码的页 | 解码后的节点 |
| 解码结构的寿命 | 一次操作 | 整个事务 |
| 每次修改 | 解码、修改、重新编码该页 | 只修改节点中的切片 |
| 分裂 | 每次修改时可能发生 | 提交时统一进行 |
| 实现代价 | 页存储增加一个操作 | 一整层节点代码及父子指针 |

两者思路相同——第一次碰到时复制一份归事务所有，之后直接改这份。复用页号消除的是**页号**的浪费（不再产生过时页）；同一事务对同一页修改 100 次，仍要解码、编码 100 次，这部分**重复编码**的开销只有节点层能省掉（编码 1 次）。

## LSM 中的对应

LSM 没有事务内过时页的问题，原因与上表对应（概念见 [B+Tree 与 LSM](../06-storage-comparisons/03-btree-and-lsm.md)）：

- **memtable 相当于内存节点**：写入先修改内存中的可变结构，不产生磁盘页。
- **flush 相当于 spill**：memtable 写满后一次性生成不可变的 SST，只写一遍。
- **WriteBatch**：一个批次的全部操作编码为一条 WAL 记录，带起始序号与自身的校验和，整条有效或整条无效，原子性由此而来。批次中的操作全部插入 memtable 后，才推进"已发布的最大序号"，此前读者看不到该批次的任何部分。
- **group commit**：多个写者同时提交时，由其中一个把各自的记录合并写入 WAL，只做一次 fsync。

本项目的"一次 meta 写入"对应 LSM 的"一条 WAL 记录加一次推进序号"。
