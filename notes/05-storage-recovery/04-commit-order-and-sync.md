# 提交顺序与同步

状态：部分已整理 · 代码：[tx.go](../../btree/tx.go) 的 `commit`；[pager.go](../../pager/pager.go) 的 `WritePage`、`Sync`

发布到磁盘的三个条件（新页先于 meta 落盘、meta 不撕裂、旧树的页不被改）见 [根分裂与发布](../04-btree-tree/04-root-split-and-publication.md#发布到磁盘上的条件)。本篇讲这些条件在 mmap 与 fsync 下怎样落实。

## mmap 写入：改即交出

`MAP_SHARED` + `PROT_WRITE` 映射得到的内存就是内核页缓存本身，不是副本。对它的一次普通内存写，效果等同 `pwrite`：该页立即成为脏页，内核随时可以写回（内存紧张、周期刷盘），数据库无法控制时机。经 mmap 写入时，没有"先私下改好、确认后再交出"的缓冲区。

`fsync` 保证返回时文件所有脏页都已落盘，但不保证刷写顺序，崩溃也可能发生在刷写中途。

## CoW 下各类页被提前写回的后果

| 页 | 提前写回的后果 |
| --- | --- |
| 新页（写在空闲位置） | 无害。磁盘上的 meta 仍指向旧树，新页无人引用，断电后只是垃圾页 |
| 旧树的页 | CoW 不修改它们，不存在脏页 |
| meta 页 | 危险。meta 是唯一原地修改的页，若先于新页落盘，断电后 meta 指向磁盘上不存在的树 |

这正是 shadow paging 能与 mmap 共存的原因：CIDR 2022 mmap 论文把 shadow paging 列为应对 mmap 写回失控的办法之一。论文针对的主要是原地更新 + WAL 的引擎：WAL 要求日志先于数据页落盘，而 mmap 下脏数据页随时可能先写回，这条规则无法保证。

## 单次 fsync 的错误

meta 与新页在同一次 fsync 中刷写时，顺序不确定：

```
改新页、改 meta → fsync 先刷了 meta → 断电 → 新根页未落盘
重启后 meta 指向的根页为全零，整棵树不可读
```

正确顺序：

```
写新页 → fsync（屏障）→ 写 meta → fsync → 报告成功
```

经 mmap 写入时还有一条纪律：**第一次 fsync 返回之前不能改动 meta 的任何字节**，改动即成为脏页，可能在屏障之前写回。遵守它，经 mmap 写也能得到正确顺序；问题在于"修改"与"交出"是同一个动作，顺序只靠代码自律，没有机制保护。

## 可写映射与借用切片

读路径把 value 作为指向页内的切片借给调用者（见 [value 借用](../04-btree-tree/02-root-and-tree-search.md#value-借用还是复制)）。若映射可写，调用者写这个切片就直接修改了数据库文件中的活页，破坏 CoW"旧页不变"的前提；若映射只读，同样的写会立即段错误，错误暴露而不是静默损坏。

## 工业对照：bbolt

| 环节 | bbolt v1.5.0 |
| --- | --- |
| 映射 | 只读：`PROT_READ` + `MAP_SHARED`（[bolt_unix.go](https://github.com/etcd-io/bbolt/blob/v1.5.0/bolt_unix.go) 的 `mmap`） |
| 写数据页 | `tx.write` 用 `writeAt`（pwrite），不经 mmap |
| 屏障 | 数据页写完后 `fdatasync`（故障注入点 `beforeSyncDataPages`） |
| 发布 | `tx.writeMeta` 用 pwrite 写 meta，再 `fdatasync`（故障注入点 `beforeSyncMetaPage`） |

读用 mmap 零拷贝，写用 pwrite 自己掌握顺序；只读映射同时防住借出的切片被改写。两次 sync 前的故障注入点用于测试"在这里崩溃"的恢复结果。Linux 上 `fdatasync` 只刷数据与恢复所需的元数据（如文件长度），比 `fsync` 少一次 inode 时间戳写入。

## mmap 在读路径上的其他代价

论文中的另外几点与写入无关，对只读映射同样成立：缺页时线程同步阻塞于 I/O，无法异步；读盘出错以 `SIGBUS` 信号出现，而不是返回错误；多核下取消映射或页换出引起 TLB shootdown。这些在自管缓存对照（B08）中展开。

## fsync 失败后不能重试

写回脏页失败时，Linux 上常见文件系统（如 ext4、XFS）会把这些页标记为干净或直接丢弃，错误只向调用者报告一次：

```
WriteAt：页进入页缓存，标记为脏
内核写回 → 设备返回 EIO → 页被标记为干净（或丢弃），记下错误
fsync → 返回 EIO
再 fsync → 没有脏页 → 返回 0（成功）
```

第二次 fsync 的成功只表示"没有待写回的脏页"，不表示数据在磁盘上。无限重试只会在某次得到一个假的成功。这一问题称为 fsyncgate：PostgreSQL 长期"出错重试 fsync"，2018 年发现后改为 fsync 失败即 PANIC，重启后从 WAL 重新写入。*Can Applications Recover from fsync Failures?*（USENIX ATC 2020）系统测试了多种文件系统与应用，发现很多程序处理不当。具体行为因内核版本与文件系统而异。

**原则：fsync 失败后，不信任"重试同步"，只信任"从自己掌握的源头重新写入"。**

本项目的提交符合这一原则：

- **写 meta 之前失败**：回滚，下一个事务从同一高水位分配页号，用 WriteAt 重新写入完整的页，使之重新变脏，由下一次 fsync 真正写下。内核丢掉的那些页无人引用，不影响正确性。
- **写 meta 之后失败**：meta 页的状态不可知，重试 fsync 也不能使其可知，只能进入失败状态、关闭重开——与 PostgreSQL 的 PANIC 同一思路。

## 两次 fsync 能否合并成一次

一次 fsync 内部的写入顺序没有保证。只 sync 一次时，断电后可能出现 meta 已落盘且校验和正确、而它指向的数据页未落盘的状态：meta 的校验和只证明 meta 自身完整。

**合并的前提：打开时能发现"最新 meta 指向的页不完整"，并退回另一份 meta。**

- **只需校验上一次事务写的页。** CoW 的一次提交写出的新页正是从新根向下的若干路径，彼此相连地挂在新根下。打开时从根向下，遇到新页就校验，遇到旧页即停，代价与上次事务写出的页数成正比。
- **难点是残留的旧页。** 失败事务的页号会被重新分配，某个位置上可能残留一张校验和正确的旧页；新页未落盘时读到的就是它，单靠页自身的校验和发现不了。ZFS 的做法是**父指针中存子块的校验和**（整棵树成为 Merkle 树），残留旧页与父指针中的校验和不符即被发现。

| | 两次 fsync（bbolt、本项目） | 一次 fsync + 校验 |
| --- | --- | --- |
| 提交延迟 | 两次刷新设备缓存 | 一次 |
| 页格式 | 不变 | 每页或每个父指针加校验和 |
| 打开时 | 只校验 meta | 从根校验上次事务写出的页 |
| 额外收益 | 无 | 能发现位翻转等静默损坏 |

降低提交延迟更常见的办法是 group commit：多个事务合并为一次提交，分摊两次 fsync（见 [原子写批次](06-atomic-write-batches.md)）。

## WAL 为什么一次 fsync 就够

WAL 提交时只 fsync 日志，数据页之后由 checkpoint 原地写回；数据页 fsync 之后，对应的日志才能删除。"第二次 sync"被移出了提交路径。

日志本身同样面对"一次 fsync 内部无序"：前面的块可能未落盘，而最后的提交记录已落盘。它仍然安全，关键在于恢复时**如何找到**提交记录：

- **meta 在固定位置**，打开时直接读取。无论它指向的页是否完整，meta 都能被直接读到。
- **WAL 按顺序扫描**，每条记录带校验和，**遇到第一条坏记录即停止**。前面有记录未落盘，扫描就停在那里，到不了后面的提交记录，该事务视为未提交。

日志中的位置编码了顺序：**中间有洞就到不了后面**，因此不需要额外的屏障。代价是要防止被重复使用的日志文件中残留的旧记录被误认：记录带序号或随机盐值（SQLite WAL 帧头的 salt、PostgreSQL WAL 页头的地址），对不上即视为日志末尾——与上面"残留旧页"是同一问题。

## LSM 中的对应

- **前台写入**：一个写批次编码为一条 WAL 记录，一次 fsync，原理同上。
- **后台 flush 与 compaction**：新 SST fsync 之后，才向 MANIFEST 追加记录并 fsync——与本项目"数据页 → sync → meta → sync"相同，只是不在用户请求路径上（概念见 [B+Tree 与 LSM](../06-storage-comparisons/03-btree-and-lsm.md)）。
- **fsync 失败**：RocksDB 将其记为 background error 并停止写入，与本项目的失败状态同类。
