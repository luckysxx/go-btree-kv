# 笔记 02：原子性 ≠ 并发控制

> 数据库教学里常被搞混的两件事。第 1 章的 `SaveData` 系列**只解决原子性 + 持久性**，
> 完全不解决并发。并发是后面"事务"章节的内容。

---

## 核心区分

| 概念                | 解决什么问题                  | 第 1 章手段           |
| ------------------- | ----------------------------- | --------------------- |
| **原子性 (Atomicity)** | 一次操作要么全做要么全不做，不出现"做一半"的中间态 | 写临时文件 + rename   |
| **持久性 (Durability)** | 操作成功返回后，断电也不丢   | `fsync` 文件 + 父目录 |
| **并发控制**         | 多操作交错时不互相踩          | **第 1 章不解决**     |

---

## 场景 1：rename 是原子的 → 文件不会损坏 ✅

进程 A、B 同时调用 `SaveData3(path, ...)`：

```
A: 写 path.tmp.111 → fsync → rename(path.tmp.111, path)
B: 写 path.tmp.222 → fsync → rename(path.tmp.222, path)
```

- 用了 `O_EXCL` + 随机后缀 → 两个临时文件不冲突。
- 两个 rename 都成功，但**后执行的赢**。
- 最终 `path` 指向 A 或 B 之一的完整内容，**绝不会是 A、B 混合**。

→ "文件不撕裂"这个目标达成。

---

## 场景 2：lost update（更新丢失）问题 ❌

```
时刻 1：A 读 path，拿到 {x: 1}
时刻 2：B 读 path，拿到 {x: 1}
时刻 3：A 改成 {x: 2}，SaveData3 写回
时刻 4：B 改成 {x: 3}，SaveData3 写回   ← 覆盖了 A 的修改
最终：path 是 {x: 3}，A 的更新永远丢了
```

- 每一步**单看**都是原子的、持久的。
- 但 A 的更新被默默覆盖了。
- 这就是 **lost update**。

---

## 真实数据库怎么办？

1. **单进程独占文件**：用文件锁 `flock` / pid 文件，保证整个数据库同时只有一个进程打开（SQLite、LevelDB 都是这样）。
2. **进程内多线程并发**：靠**事务 + 锁 / MVCC**。
   - build-your-own DB 走简单路线：B+Tree 的 Copy-on-Write + 一把全局写锁。
   - PostgreSQL / MySQL InnoDB：MVCC（多版本并发控制）。

## 教学法提示

技术书常见套路：**先把一个维度讲透，再叠加下一个维度**。
- 第 1 章只解决"单次写入的原子性 + 持久性"。
- 后面叠加：分页、B+Tree、Copy-on-Write、事务……
- 看到一个"漏洞"先别慌，可能是作者故意留到后面章节解决的。
