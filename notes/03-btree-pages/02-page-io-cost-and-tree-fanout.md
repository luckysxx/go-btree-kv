# 页访问成本、扇出与树高

状态：已有正文（模型笔记，无性能测量）

前置：[搜索模型与索引取舍](01-search-models-and-index-tradeoffs.md)。下面是量级模型：固定扇出、比较成本、占用率和缓存都会影响估计；树高是整数，公式给出的是尺度。

## 从内存二叉树到页组织

n = 10⁹ 时，平衡二叉路径约 log₂(10⁹) ≈ 30 层（量级示意，不是红黑树高度的保证）。若路径上每个节点都要读一张未缓存的页，层数就对应潜在的页访问次数。实际磁盘 I/O 还取决于缓存和布局，不能把每次下降都等同于一次随机 I/O。

几十字节的节点却要读入一整页 4 KiB，页的利用率很低（若多个节点同处一页或页已缓存则另算）。思路是：既然一次访问至少拿到一页，就把这一页塞满 key，一个节点几百个孩子，树立刻变矮。B+Tree 让一个节点占一页，用较大扇出减少路径上的页访问。"把红黑树压扁"只是形象类比，不是构造算法。

## 扇出、树高与页内比较

| | 二叉平衡树 | B-Tree（每节点最多 B 个孩子） |
| --- | --- | --- |
| 层数 | log₂n | log_B n（更少） |
| 每层比较 | 1 次 | 节点内二分，log₂B 次 |
| 总比较 | log₂n | log_B n × log₂B |

换底：

```
log_B n × log₂B = (log₂n / log₂B) × log₂B = log₂n
```

这也是 O(log n) 从不写底数的原因：换底只差常数因子。

n = 10⁹、B = 100 的量级示例：

```
层数:    log_100(10⁹) = 9/2 ≈ 4.5 层     （二叉约 30 层）
每层:    100 个 key 里二分 ≈ 6.6 次
总比较:  4.5 × 6.6 ≈ 30 次               ← 仍是 log₂(10⁹)
```

4.5 是尺度，不是实际层数或 I/O 次数。

**B-Tree 优化的不是比较次数，而是"比较被分装进多少个要访问的节点"。** 比较模型下的 Ω(log n) 下界没有被绕过：

```
二叉树:   30 次比较，分散在 30 个节点（每节点 1 次）
B-Tree:   30 次比较，集中在约 4.5 个节点（每节点约 6.6 次）
```

若每个节点访问都需要读取未缓存的页，减少页访问就可能减少昂贵的 I/O；真实 I/O 次数需要观测。

## 与本项目页实现的关系

Pager 按 4 KiB 分页，B+Tree 的一个节点就是一页。[节点字节布局](03-node-format-and-record-addressing.md) 决定 4096 字节里怎么排尽可能多的 key 和孩子页号，让一次页访问服务更多 key。读取未驻留的文件页可能很贵，已驻留页的访问不等于磁盘 I/O。

本项目使用变长 key/value、按字节容量分组，因此不能用固定阶数计算实际孩子数；父目录容量如何限制生长见 [内部页分组与 key 上限](12-internal-grouping-and-key-limit.md)。实际树高随记录长度、占用和数据量变化，"3～4 层"只是直观量级。

## 常见误区

- "B-Tree 减少了比较次数"：总比较仍是对数量级，减少的是访问的节点数。
- "每次下降都会缺页 / 都是一次 I/O"：取决于缓存与布局。
- 把 4.5 层这样的小数当作实际层高或测量结果。
- "按页组织是唯一正确的选择"：它是页访问成本远高于比较成本时的合理选择，其他方案见 [存储结构对照](../06-storage-comparisons/README.md)。
