# 搜索模型与有序索引的取舍

状态：已有正文（模型笔记，无单独实现）

## 适用范围与成本假设

这里讨论比较查找与哈希的模型区别，以及有序数据的查找/修改取舍。比较查找的下界指所述决策模型的**最坏情况渐近下界**；不表示每次命中都需要相同次数。哈希的常数期望代价依赖散列、负载与所采用的单次操作成本假设，变长 key 的计算/比较成本不能凭 O(1) 字样消失。

实际页访问成本另见 [页访问、扇出与树高](02-page-io-cost-and-tree-fanout.md)，不把下面的简化模型当成唯一选型条件。

## 1. 两个世界：比较 vs 计算

你能对 key 做什么操作，决定了你属于哪个世界，也决定了你逃不逃得过 log n。

| 世界 | 允许的操作 | 代表结构 | 受 log n 铁底约束？ |
|---|---|---|---|
| **比较世界** | 通过 key 的比较区分候选（下文按二分支问题计数） | 有序数组、二分、比较式树索引 | 最坏情况 Ω(log n)，常数取决于比较模型 |
| **计算世界** | 能对 key 做**计算**（`hash(k)`、`k` 当下标） | 哈希表、直接寻址 | 不受该比较下界约束；满足假设时可有常数期望代价 |

> 这是整件事的分水岭。"log n 改不了"只统治比较世界。hash 能 O(1)，
> 不是因为它"更聪明"，而是因为它**换了个世界**，根本不在那棵决策树里。

## 2. 比较查找的决策树下界

### 2.1 任何比较式算法都是一棵决策树

不管算法多巧（二分 / BST / 跳表 / 任意），只要**只靠比较**，执行过程一定是：

```
              x < a₃ ?
             /        \
          yes          no
          /              \
      x < a₁ ?         x < a₅ ?
      /     \          /     \
    叶子   叶子      叶子    叶子
```

- 每个**内部节点** = 一次比较（一个 yes/no）
- 每个**叶子** = 一个最终答案
- **某次查询做了多少次比较 = 根到叶子的路径长**
- **最坏比较次数 = 树高 h**

### 2.2 计数论证（数学核心）

在下述“返回命中位置或不存在”的搜索模型中，n 个不同 key 至少对应 **n+1 种答案**（第 1..n 个位置，或不存在）。
不同答案必须落在**不同叶子**上（否则算法分不清 → 会答错），所以：

```
叶子数 L ≥ n+1
```

而二叉树（每次比较 2 个分支）高度 h 最多撑出 2^h 个叶子：

```
L ≤ 2^h
```

两式相夹：

```
2^h ≥ L ≥ n+1   ⟹   h ≥ log₂(n+1) = Ω(log n)
```

### 2.3 怎么理解这个铁底

> 20 个 yes/no 问题最多区分 2²⁰ ≈ 100 万样东西。
> 想区分 10 亿样，**无论问得多巧，至少问 30 次**（log₂10⁹ ≈ 30）。

- **有序数组 + 二分**：最坏情况 Θ(log n)，达到这里的渐近下界；精确次数取决于比较操作和接口约定。
- **平衡 BST**：Θ(log n) → 也最优
- **退化 BST（链）**：O(n) → 没把决策树建平衡，**白白浪费了树高**

> 补充：排序的 Ω(n log n) 是同一个论证，答案有 n! 种排列 → 叶子 ≥ n! → h ≥ log₂(n!) ≈ n log₂n。同一把尺子。

## 3. 树到底从哪冒出来的（解决"为什么搜索就是树"的卡点）

### 3.1 一次比较 = 一次分叉，"一连串分叉"的形状定义上就是树

靠比较搜索，本质是**一步步排除候选**，每个比较排除一部分候选；平衡选择可让候选范围大致减半。把这个决策过程画出来，
**它本身就是一棵二叉树**。不是你选择用树，是"一串 yes/no"在数学上的名字就叫树。
**只要用比较搜索，你就已经在走一棵树了**，无论有没有意识到。

### 3.2 二分查找其实也是树，只是隐形的

```
有序数组: [1, 3, 4, 6, 7, 8, 10, 13, 14]   ← 没有指针，就是一排数

它二分时走的路（原图仅示意部分层次，未画出 4、8）：
         7         ← 中点
       /   \
      3     13
     / \    / \
    1   6  10  14
```

- **有序数组 + 二分** = 把这棵决策树**隐式**藏在下标计算里
- **BST** = 把同一棵树**显式**用节点 + 指针**摆出来**

→ 所以"为什么是树"的答案是：**它一直是树**，区别只在"算出来"还是"摆出来"。

### 3.3 那为什么要费劲摆出来（真建树）？—— 为了改得动

二分查找已经是树了，数组还更省内存，为什么发明 BST？
这里用**插入/删除的成本**解释一个主要动机。

```
有序数组插入 5：[1,3,4,6,7,...] → 6 后面全往后挪 → O(n) 💀
```

数组的"连续"是二分快的本钱，**也是改不动的诅咒**。
把树用指针组织后，局部插入不必整体搬动数组；查找插入点及维护平衡的代价仍要计入。平衡树的操作可控制在 O(log n)。

> **树 = 把比较决策过程显式组织成节点与引用，**
> **好让它在保持有序的同时还能廉价增删。**

## 4. 内存世界的树：BST → 平衡 BST

### 4.1 BST 三件套

- **查找**：比 key 小往左，大往右，O(树高)
- **插入**：走到底挂上去
- **删除**：三种情况
  - 无孩子：直接删
  - 一个孩子：孩子顶替
  - 两个孩子：找**中序后继**（右子树一路向左到底）的值复制过来，再去右子树删那个后继（它最多一个右孩子，退化成前两种）

**死穴**：按顺序插入（自增 ID！）→ 退化成链 → 搜索掉回 O(n)。
→ 必须**强制平衡**。

### 4.2 平衡 BST（AVL / 红黑）：代价在修改，好处是搜索被保证快

平衡是**为了救搜索**（别退化成 O(n)），代价付在**修改**上：

```
普通 BST 插入:  走到底，挂上 → 完事            （便宜，但可能歪成链）
平衡 BST 插入:  走到底，挂上 → 发现歪了 → 旋转掰正  （多花力气换"搜索永不退化"）
```

**旋转**：只改几个指针，O(1)，且**不破坏中序有序性**（这是它能用的根本原因）。

```
      y                 x
     / \               / \
    x   C   右旋 →     A   y
   / \                    / \
  A   B                  B   C
```

> 一句话：**平衡树 = 每次修改多花点力气（旋转），来买"搜索永远快"的保证。**
> （不是"修改廉价、搜索慢"，是反过来。）

### 4.3 AVL vs 红黑：真正的"搜索快 ↔ 修改便宜"跷跷板

| | AVL | 红黑树 |
|---|---|---|
| 平衡卡得 | 严（左右高差 ≤ 1） | 松（最长路 ≤ 2×最短路） |
| 高度约束 | 更严格 | 较宽松 |
| 修改维护 | 维护高度平衡 | 维护颜色/路径约束 |
| 选型倾向 | 倾向讨论读取成本 | 倾向讨论综合更新成本；不是无条件性能结论 |

常见的说法是"某语言的 map、某内核、Java TreeMap 用红黑树"，具体实现要按语言、组件和版本核实；读多写少也不直接等于必须用 AVL。

红黑树的 5 条颜色规则**不用背**：记住"它用染色+偶尔旋转把树高控制在 2 倍最优内"即可。要写的时候再查。

## 5. 计算世界的 hash：凭什么 O(1)、代价是什么

hash **根本不问大小**，不在决策树里，§2 的铁底管不到它：

```
查 k:  i = hash(k)     ← 一次算术，直接算成下标
       看 table[i]      ← 一次数组访问
```

### 数学：为什么期望 O(1)

表大小 m，存了 n 个，**负载因子 α = n/m**。拉链法 + 均匀 hash：

```
每槽期望挂 α 个
一次查找 = 算 hash(1) + 扫链(期望 α) = 1 + α = Θ(1)   （α 是常数时）
```

在均匀散列、负载有界及相应操作成本假设下，查找可有常数期望代价；扩容的代价还需在一串更新上摊销。

### 三笔代价（取舍）

1. **丢掉顺序** 💀 最致命 —— hash 把 key 打散，相邻 key 离十万八千里 →
   普通哈希表不直接提供有序范围、前驱后继或有序遍历；若逐项扫描或另建索引，成本与能力要另算。
2. **最坏退化** —— 全撞一个槽 → O(n)。靠好 hash 兜住"期望"，但最坏仍 O(n)；
   平衡比较树提供**最坏 O(log n)** 的查找界；普通未平衡 BST 没有这个保证。
3. **空间换时间** —— α < 1 总有空槽浪费，扩容 rehash 要重算全部。

## 6. 全景表（理想扁平模型：每次操作记 1 单位，摸节点免费）

| 结构 | 世界 | 查找 | 插入 | 删除 | 有序？ |
|---|---|---|---|---|---|
| 无序数组 | 比较 | O(n) | 摊销 O(1) 追加 | 已知位置时 O(1) 换末尾；先找 key 另计 | ❌ |
| 有序数组 | 比较 | Θ(log n) **最优** | O(n) 挪 | O(n) 挪 | ✅ |
| BST（不平衡） | 比较 | 最坏 O(n)；平均情况需输入分布假设 | 同左 | 同左 | ✅ |
| 平衡 BST | 比较 | Θ(log n) **保证** | Θ(log n) | Θ(log n) | ✅ |
| B-Tree | 比较 | Θ(log n) | 查找为对数比较；每个受影响节点有 O(B) 搬移，级联总成本另计 | 同左，含可能的多层合并/重分配 | ✅ |
| 哈希表 | **计算** | Θ(1) 期望（模型假设下） | 常数期望/摊销（含扩容条件） | 常数期望（模型假设下） | ❌ |

**注意 B-Tree 那行**：扁平模型下它的操作数和平衡 BST 一样，还多了"节点内搬移"和"半满浪费空间"。
这张表刻意没有计算局部性和页访问差异，因而不能单靠它排除 B-Tree。页访问维度在下一篇恢复；它不是结构价值的完整模型。

## 7. 选型图：先问是否需要有序访问

```
需要"有序"吗？(范围查 / 前驱后继 / 最小值 / 有序遍历)
│
├─ 不需要，只点查  ──────────►  哈希表        期望 Θ(1)（散列和负载假设下）
│
└─ 需要，且仅靠比较定位 ──► 最坏下界 Ω(log n)
              │
              ├─ 数据静态  ──►  有序数组+二分   Θ(log n)，最简
              │
              └─ 数据动态  ──►  平衡 BST        Θ(log n)，三操作全保证
```

- **需要顺序且按比较查找**：平衡 BST（动态）和有序数组（静态）可达到上述模型的渐近下界；这不是全部可选结构。
- **只需点查**：满足散列和负载假设时，可考虑常数期望代价的哈希表；普通哈希表不直接保持 key 顺序。

**接下来增加一个重要维度：访问一个节点相对比较一次 key，成本是多少？**
- 暂不计节点访问成本 → 用红黑/AVL 等结构讨论比较和修改成本
- 摸节点很贵且能批量拿（磁盘页 / cache line）→ B-Tree / B+Tree

## 常见误区

- "比较搜索一定 ≥ log₂n 次"：下界是最坏情况的渐近下界，个别查询可以更少。
- "每次比较砍掉一半"：只有平衡的选择才大致减半，退化的树可能每次只排除一个。
- "显式树的唯一理由是增删"：增删成本是主要动机之一，不是全部。
- "AVL 一定更快、红黑更新一定更便宜"：两者是高度约束与维护成本的取舍，结论依赖负载与实现。
- "BST 平均 O(log n)"：平均情况需要输入分布假设，任意输入下没有这个保证。
