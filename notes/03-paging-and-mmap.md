# 笔记 03：分页存储 + mmap 的心智模型

> ch01 已经能 crash-safe 地存"整个文件"，但每次改 1 字节就重写 1GB → 不可用。
> ch02 要解决这个：把文件按 4KB 切分成 page，每次只改需要改的页。

---

## 1. 重置认知：文件就是一串字节

文件系统层面，文件只有一种东西：**从 offset 0 到 N-1 的字节序列**。
没有"行"、"列"、"页"、"表"——这些都是上层软件**脑补**的。

**同样的字节，不同的"解读规则"得到不同数据**：
- 按 ASCII 解读 → 字符
- 按 int32 解读 → 整数
- 按数据库的页布局解读 → B+Tree 节点

这个"解读规则"就是**文件格式 (file format)**。

---

## 2. 文件是可随机访问的

不是磁带、不是流。`lseek(fd, offset, ...)` 能跳到任意位置 read/write。
**这是分页可行的前提**。

---

## 3. "页 (page)" 是什么？纯约定

**就是把字节流每 4096 切一刀，假装每段是独立单位**。

文件里**没有任何东西**把页分开——没分隔符、没页头标记。
"页"只存在于读这个文件的代码的脑子里。

**page 编号 ↔ 文件 offset 是纯算术关系**：
```
page N 的字节范围 = [N*4096, (N+1)*4096)
读 page N      = lseek(fd, N*4096) + read(4096)
```

→ O(1) 定位任意一页。

**为什么是 4KB？** 全栈对齐：
- SSD 最小写入单位 ≈ 4KB
- 操作系统内存管理单位 = 4KB (page size)
- 文件系统 block 通常 4KB
- → 选 4KB 时四层对齐，性能最优

---

## 4. 一页里放什么？数据库自己说了算

每个数据库设计自己的页布局。本书 B+Tree 节点页大概：

```
一个 page (4096 字节) 内部：

  byte 0    byte 2     byte 4              byte 4096
   ├────────┼─────────┼─────────────────────┤
   │ 类型    │ 记录数  │  key/value 内容...   │
   │ 2字节  │ 2字节   │  ...                 │
   └────────┴─────────┴─────────────────────┘
```

**怎么布局完全是设计选择**。前面几字节存元信息，后面存数据。
具体格式 ch03 一字节一字节设计。

---

## 5. Bootstrap 问题：怎么找到元信息？

**问题**：数据库重启时，怎么知道 B+Tree 的根 page 在哪？
"存在元信息里" → 元信息又在哪？ → 元信息的元信息？无限递归。

**解决**：**约定**。所有数据库规定：
> **文件的第一页（offset = 0）永远是元信息页 (meta page / superblock)**。

启动代码**写死从 offset 0 读 4096 字节**，不需要"找"。
- ext4 → superblock
- SQLite → database header
- PostgreSQL → pg_control
- 本书 → meta page

**为什么这样就够了？**
"meta page 在 offset 0" 这件事**不是数据，是代码**——
写死在程序里，不会丢、不会损坏。

> 普遍规律：所有持久化系统最底层都有一个**硬编码的入口点**。
> ch01 的 rename 也一样——靠"文件系统自己知道根目录在哪"这个底层入口点切断递归。

---

## 6. mmap：让文件"变成"一个数组

### 不用 mmap (传统 read/write)

```go
buf := make([]byte, 4096)        // 1. 用户态分配 4KB
fp.ReadAt(buf, 42*4096)           // 2. 内核 page cache → buf (1 次拷贝)
buf[0] = 0xff                      // 3. 改内存
fp.WriteAt(buf, 42*4096)           // 4. buf → 内核 page cache (1 次拷贝)
```

每次读写：1 次系统调用 + 1 次内存拷贝。

### 用 mmap

```go
data, _ := syscall.Mmap(fd, 0, fileSize, PROT_READ|PROT_WRITE, MAP_SHARED)
// data 是 []byte，长度 = 文件大小
// 这个 []byte 直接指向内核 page cache，零拷贝
page42 := data[42*4096 : 43*4096]
page42[0] = 0xff                   // 直接改 page cache，内核自动标脏
```

零系统调用、零拷贝。改字节就是改 page cache。

### 按需加载 (lazy / demand paging)

mmap 返回的是**虚拟地址**，不立刻占物理内存。
- 映射 1TB → 进程虚拟地址空间占 1TB（虚拟空间富得很，~256TB）
- 只有**真正访问到的 4KB**，内核才从磁盘读进物理内存（**page fault**）
- 没访问的部分，物理内存 0 占用

→ 打开 1TB 文件 mmap 是**瞬间完成**的。

### 比喻

- **没 mmap**：图书馆员把书复印一份给你（拷贝），你看完改完，他再复印你改的部分回原书（再次拷贝）。
- **有 mmap**：给你直通仓库的钥匙，你直接在原书上改。

---

## 7. mmap 不解决持久性！

> ⚠️ 这是最常见的误解。

`data[100] = 0xff` 只是改了 **page cache 里的字节**，
内核标这页为"脏页"，**但什么时候真正写回磁盘是内核自己决定的**
（通常 30 秒后、内存压力大时、或显式 `msync` / `fsync`）。

→ 改完没 `fsync`，断电就丢。

**mmap 改变的是访问方式，不是持久性语义**。
ch01 学到的 `fsync` 在 ch02 一样关键——B+Tree 的事务提交点就是决定"何时 fsync"。

### ⚠️ "看不出差别" 才是真相

把 `fsync` 注释掉，`cat` / `hexdump` 显示的内容**和 fsync 完全一样**。
这不是 fsync 没用，而是：

| 谁读 | 数据来源 | 是否依赖 fsync |
| ---- | -------- | -------------- |
| 同机器另一进程 (cat/hexdump) | Page Cache | 否 (内存里同一份) |
| 程序退出后再开 (page cache 还在) | Page Cache | 否 |
| **机器断电/重启后** | **磁盘** | **是 ← 这才暴露丢失** |
| 拔硬盘到另一台机器读 | 磁盘 | 是 |

**fsync 决定的不是"别人能否看到"，而是"断电后还在不在"**。
这就是 fsync 最阴险之处：bug 只在最坏的时刻暴露。

也是为什么数据库测试需要**物理断电测试设备**——
任何系统调用（包括 `sudo purge`）都模拟不了真正的断电，
因为内核在退出前总会优雅地把 dirty page 刷盘。

---

## 8. mmap 的坑

1. **磁盘 IO 错误不是 error，是 SIGBUS 信号**（访问已删除文件、磁盘坏块时）
2. **文件 grow 时要重新 mmap**（已映射区域大小不能直接变）
3. **跨平台 API 不同**（Linux / macOS / Windows）
4. **进程崩溃 = 不一致风险**（不像 read/write 走系统调用有完整事务语义）
