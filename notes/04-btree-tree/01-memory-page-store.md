# 内存页存储：页号、内容所有权与按号读取

状态：已有正文 · 代码：[pagestore.go](../../btree/pagestore.go)

## 要解决的问题

页函数只处理字节：`internalChild` 从父目录选出孩子的**页号**，而 `leafGet` 等函数需要的是那张页的 `[]byte`。页存储负责把两者接起来：按页号找到页内容。

它是一个很薄的一层，只做"页号 → 整页字节"的映射，不按用户 key 查找记录。页号找不到属于页引用或存取错误，不等于用户 key 不存在；key 是否存在，要在成功读到合法叶子页之后，由页内查找判断。

## 和 MMU、块设备的类比

页存储也是"把一个编号翻译成一段字节"，但它更接近文件系统里的 `bread(dev, blockno)`，而不是 MMU：

| | MMU | 页存储 | xv6 `bread` |
| --- | --- | --- | --- |
| 编号从哪来 | CPU 每次访存隐式使用 | 父页里显式存着孩子页号 | inode 里显式存着块号 |
| 谁来翻译 | 硬件，代码无感 | 树代码主动调用读取 | 文件系统代码主动调用 |
| 只读怎么保证 | 页表权限位，硬件强制 | 只靠约定 | 约定与锁 |

接入 Pager 后两层并存：上层是自己的页号，页号 × 4096 得到 mmap 区域中的偏移，再往下的虚拟地址 → 物理页翻译由 MMU 和内核完成。

## 接口

```go
func newMemPageStore() *memPageStore
func (s *memPageStore) save(page []byte) (uint64, error) // 复制整页，分配新页号
func (s *memPageStore) get(id uint64) ([]byte, error)    // 返回借用的只读视图
```

**save 不接受调用者指定的页号。** 存储自己分配页号，接口里没有覆盖已有页的途径，CoW"新版本写新页号、旧页不变"由接口形状保证，而不是靠调用者自律。反例：若接口是 `put(id, page)`，树代码某处页号算错，把新内容写进仍被旧根引用的页，旧版本就被悄悄改掉，没有任何报错。

**先用具体类型，不定义 interface。** 磁盘版本（批次 4）还需要回收、提交等能力，现在猜接口多半要改；等第二个实现出现时，在使用方按实际需要抽取即可，Go 的隐式接口让这一步很便宜。

## 保存时复制，读取时借用

- **保存时复制。** 不能只写 `pages[id] = p`：Go 的切片赋值共享底层数组，调用者之后复用或修改 `p`，会悄悄改掉已保存的页。复制让存储拥有自己的字节。
- **读取时借用。** 每次读都复制 4096 字节代价太高，所以返回存储内部字节的切片。Go 的 `[]byte` 不强制只读，调用者必须遵守"不修改返回值"的约定。`getKey`、`getValue`、`leafGet` 返回的子切片同样引用原页，受同一约束。

CoW 更新的局部过程：读取页 7 → 页重建函数构造新字节 → 保存为新页号 8，页 7 不变。把父目录改为引用 8 是上层树更新的职责，保存成功本身不修改父目录。

## 页号生命周期

- 从 1 开始递增，0 永不分配，与内部目录"孩子页号非零"的约定一致。
- 暂不回收：旧页可能仍被旧根或读者引用，何时能安全回收要等删除（D06）与读事务、空闲页管理（批次 4）。
- uint64 按每页 4 KiB 不可能耗尽，不做回绕检查。
- 失败的 save 不消耗页号。

新页是内存中的一张新页；将来磁盘 CoW 也不是每次复制整个数据库文件，而是把新页写到文件中的空闲位置。页号的分配由页存储负责，目录整理函数（如 `internalReplaceChild`）只接收已经分配好的页号。

## 错误

| 情况 | 返回 | 理由 |
| --- | --- | --- |
| 页长度不是 4096 | `ErrBadPageSize`，存储不变 | 短切片存进去后要到 getKey 越界时才 panic；错误离原因越近越好查 |
| 页号不存在（含 0） | `ErrPageNotFound` | 父页引用了不存在的页，说明结构出错或数据损坏，不是正常结果 |

对比 `leafGet` 用 `(value, found)`：key 不存在是正常结果。页不存在不正常，用 error；将来磁盘版本还有 I/O 错误，签名也不用改。

## 什么时候用结构体和方法

判断标准：有没有**跨调用存活、且字段之间有约束**的状态。

- 页函数没有：输入一张页、输出新页，调用之间不留任何东西。页本身是按固定格式编码的字节，将来要原样写进文件或 mmap，所以用 `[]byte` 表示最直接。类比 `bytes.Compare`、`binary.LittleEndian`、C 的 `memcpy`。
- 页存储有：`pages` 和 `nextID` 必须一起存活，并保持"nextID 大于所有已分配页号、0 不分配"。若用包级函数写成 `save(pages, &nextID, page)`，调用者可能传错搭配或用零值 nextID；结构体加构造函数把状态和约束收在一处。类比 `bytes.Buffer`、C 的 `FILE*`。`save` 用指针接收者，因为要修改 nextID。

也可以写 `type node []byte` 再挂方法，底层字节不变，只是写法选择。把页解码成结构体再修改（bbolt 的 node）才是设计上的差异：换取修改方便，付出编解码成本。

## 对照 bbolt

bbolt 源码尚未加入 references，以下依据对其设计的了解，引入源码后逐项核对。

| 方面 | 本实现 | bbolt |
| --- | --- | --- |
| 页号 | uint64，0 表示无页，从 1 分配 | `pgid`；页 0、1 是两个 meta 页，随后是空闲列表页和初始根叶子 |
| 分配 | 只增的 nextID | 先从 freelist 找连续空闲页，找不到才推高文件末尾；超大节点可占多页（overflow） |
| 回收 | 不回收 | 释放的页按写事务号挂起，更早的读事务全部结束后才复用 |
| 读取 | 借用 map 中字节，只读靠约定 | 直接指向 mmap 区域；mmap 只读映射，误写触发段错误，由 MMU 强制只读 |
| 修改 | 页函数直接在 `[]byte` 上重建 | 写事务把页解码成内存 node 修改，提交时再编码写入新页 |

## 不变量与测试

- 保存后修改输入，不影响已保存页。
- 遵守只读约定时，按号读取的内容稳定。
- 保存新版本不覆盖旧页号所指内容。

[pagestore_test.go](../../btree/pagestore_test.go)：页号 1、2 递增且读回一致；保存后把输入全改为 0xFF，已保存页不变；读旧页 → leafInsert → 存成新页号，旧页仍是旧值；0、1、4095、4097 字节被拒且不消耗页号；页号 0、未分配、极大值返回 ErrPageNotFound。故意去掉 save 中的复制时，"保存时复制"测试会失败。未覆盖：并发访问；调用者误改借用切片（Go 无法在类型层面阻止）。
