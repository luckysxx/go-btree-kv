# 根分裂与发布

状态：已有正文 · 代码：[tree.go](../../btree/tree.go) 的 `commitRoot`

## 为什么树高只在根变化

局部分裂产生的新页与原页同层，只让父页多一个目录项；只有根分裂才新建一层。所以所有叶子始终在同一深度，树长高时不需要遍历整棵树。

## 根分裂

`insert` 对根这一层返回的，和对其他层一样是一组目录项。普通的一层有父页用 `internalReplaceChildSplit` 接住它们；根没有旧父页可以替换，所以要**用这组目录项新建一张内部页**。可以把根看作一张空的虚拟父页下唯一的孩子。

```
分裂前：   根(叶子 5){a b c d e}           ← 插入 f 后装不下
insert 返回：[{a→6}, {d→7}]                ← 叶子 6{a b c}、7{d e f} 已保存
新建根：   根(内部 8)[a→6 | d→7]           ← 树高 +1
```

分裂出的两页保持原样，成为新根的孩子；新建的只有新根这一页。旧根 5 从新根不可达，但一字节未变，持有页号 5 的读者仍读到插入前的完整旧树。

## 新根一定装得下一页吗

根这一层最多返回 3 项：

- 根是叶子：`leafInsertSplit` 最多分 3 页。
- 根是内部页：最多分 2 页。替换后目录不超过 4084 + 3 × 1014 ≈ 7100 字节；贪心装页时第一页因"下一项放不下"而停，已装至少 4084 − 1014 = 3070 字节，剩余不足 4042，第二页必然装得下。

每项最多 2 + 4 + 1000 + 8 = 1014 字节，3 项加页头 12 + 3 × 1014 = 3054 ≤ 4096，所以一个 `if` 加 `internalBuild` 就够。这个结论**依赖 maxKeySize ≤ 1000**：上限放宽到 2000 时 3 项需要 6054 字节，就必须改成循环。

`if` 与循环的取舍：`if` 在假设被破坏时由 internalBuild 报 ErrPageFull，问题会暴露；循环更稳健（可一次长高两层），但假设被破坏时没有任何提示。bbolt 是循环的思路：提交写回时根节点分裂就新建父节点，并对父节点重复写回，因为它的 key/value 没有这么严格的上限、节点还可以跨多页，推不出"一定装得下"。

随机测试很难碰到"根处三路叶子分裂"，所以把这个前提写成单独的测试 `TestRootSplitEntriesFitInOnePage`：放宽 maxKeySize 时它会先失败，而随机的长 key 测试并不会。随机测试覆盖不到的前提，需要显式检查。

## 发布：只改一个根指针

`commitRoot` 是 put 与 delete 共用的**唯一**修改 `t.root` 的地方，在新根页保存成功之后执行：

| 根这一层交回 | 新根 |
| --- | --- |
| 0 项（树已删空） | 新建空叶子 |
| 多项（根分裂） | 新建内部页，树高 +1 |
| 1 项 | 就是它；若它是只有一个孩子的内部页，逐层提升孩子（根收缩，见 D06） |

构建或保存新根失败时树仍是旧版本。读者每次读都从某一个根页号出发：拿旧根看到完整旧版本，拿新根看到完整新版本，不会看到半新半旧，这就是"发布"。发布点只有一处的好处：以后发布会越来越重（读写并发时 `t.root` 的读写需要原子操作或加锁，否则是数据竞争；落盘后要先确认新页已落盘再写 meta），只改一处不会漏。

## 发布到磁盘上的条件

内存中发布是一次赋值，不存在"执行一半"，之前保存的页也都在内存里。磁盘上两点都不成立：随时可能断电；`write` 返回只代表进入页缓存，落盘时机和顺序不受控制（见 [位置、可见性与持久性](../01-file-persistence/02-data-visibility-durability.md)）。根页号放在固定位置（meta 页），发布就是改写 meta。要做到"断电后要么是完整旧树、要么是完整新树"，需要三个条件：

1. **新页先落盘，再写 meta。** 否则内核可能先写 meta，断电后 meta 指向零页或垃圾。顺序：写新页 → fsync → 写 meta → fsync → 才向调用者报告成功。第一次 fsync 是屏障，第二次保证 meta 本身持久。
2. **meta 这一写本身不能撕裂。** 4 KiB 页写到一半断电可能前新后旧（torn write），硬件通常只保证单扇区原子，且不普遍可靠。bbolt 用两个 meta 页轮流写：各含根页号、事务号和校验和，每次写较旧的那个；打开时选校验和正确且事务号更大的。新 meta 写坏就退回另一个，得到完整旧树。
3. **新 meta 落盘前，旧版本用到的页一张都不能改。** 能退回旧 meta 的前提是旧树完好。CoW 不覆盖旧页，目前满足；引入页回收后，一张页只有在任何可能被退回的版本都不再引用时才能复用（bbolt 按事务号挂起释放页，原因之一在此）。

| 断电时机 | 重启后 |
| --- | --- |
| 写新页期间，或第一次 fsync 后、写 meta 前 | meta 仍旧 → 完整旧树，新页成为垃圾 |
| 写 meta 写到一半 | 校验和不对 → 用另一个 meta → 完整旧树 |
| 第二次 fsync 之后 | 完整新树 |

经 mmap 修改的页，内核随时可以写回。新页提前写回无害（没有已落盘的 meta 引用它），危险的只有 meta：第一次 fsync 返回前不能改动它的任何字节。bbolt 读用 mmap、写用 `pwrite`，把顺序握在自己手里，详见 [提交顺序与同步](../05-storage-recovery/04-commit-order-and-sync.md)。这些条件由 E 组的双 meta 与提交顺序满足。

## 与 WAL 的区别

这套做法叫 **shadow paging**（CoW 提交），和 WAL 是解决同一问题的两种路线：

| | WAL | Shadow paging / CoW |
| --- | --- | --- |
| 数据页 | 原地覆盖 | 从不覆盖，写到新位置 |
| 提交前先写 | 把"改了什么"追加进日志并 fsync | 把新页写到空闲位置并 fsync |
| 提交点 | 日志中的 commit 记录落盘 | meta 中的根页号落盘 |
| 数据页何时写 | 可稍后批量写回（checkpoint） | 提交前必须写完 |
| 崩溃恢复 | 重放日志，补上已提交未写回的修改 | 不需重放，选一个有效 meta 即可 |

共同的骨架：由一次小而原子的写决定提交（commit 记录 / meta），并且它依赖的内容必须先落盘（日志先于数据页 / 新页先于 meta）。meta 可以看作只存一条"当前根在哪"的日志。

代价：CoW 写放大约为树高且多为随机写，换来无日志、恢复简单、读者天然看到快照；WAL 提交只顺序追加一条小记录，但要实现重放与 checkpoint，还要防护原地覆盖的 torn page（如 InnoDB 的 doublewrite）。代表：InnoDB、PostgreSQL、SQLite WAL 模式 / bbolt、LMDB。本项目中 WAL 会出现在 Raft 的磁盘日志（批次 6）与 Rust 阶段的 LSM。数据库 WAL 的内部机制（write-ahead 规则、checkpoint、重做与撤销）及其与 Raft 日志的区别见通用笔记《预写日志与复制日志》。路线比较另见 [原地更新与 CoW](../05-storage-recovery/01-in-place-update-and-cow.md)，业界选型见 [B+Tree 与 LSM](../06-storage-comparisons/03-btree-and-lsm.md)。
