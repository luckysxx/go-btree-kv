# 笔记 06：搜索数据结构的理论地基（hash / 树 / 比较的铁底）

> 进 ch03 写 B+Tree 之前，先把"为什么是树、为什么是 log n、B-Tree 到底优化了什么"
> 从数学上钉死。这是后面所有存储结构的认知地基，也是 3.0 设计动机的理论版。
>
> 卡住时回这里：所有困惑基本都源于"没分清比较世界和计算世界"，或"没分清比较次数和摸节点次数"。

---

## 0. 核心结论（先看这个，细节在后面）

1. **搜索不一定是树**。能用算术直接算出位置的（hash）根本不进树。
2. **比较式搜索一定 ≥ log₂n 次**——这是信息论铁底，不是实现问题。
3. **树 = "比较决策过程"这个天生的树形，被指针 materialize 出来，好让它在保持有序的同时还能廉价增删。**
4. **B-Tree 不减少比较次数**（那个锁死在 log₂n），它减少的是"摸节点的次数"。只有当"摸一个节点"很贵时（磁盘 IO / cache miss）才有意义。
5. **理想扁平模型下，世界只剩两个赢家**：要有序 → 平衡 BST（log n）；不要有序 → 哈希（O(1)）。B-Tree 在扁平模型里是多余的。

---

## 1. 两个世界：比较 vs 计算

你能对 key 做什么操作，决定了你属于哪个世界，也决定了你逃不逃得过 log n。

| 世界 | 允许的操作 | 代表结构 | 受 log n 铁底约束？ |
|---|---|---|---|
| **比较世界** | 只能问 `a<b? a=b? a>b?` | 有序数组、二分、所有树 | ✅ 锁死 ≥ log₂n |
| **计算世界** | 能对 key 做**算术**（`hash(k)`、`k` 当下标） | 哈希表、直接寻址 | ❌ 不在管辖内 → 能 O(1) |

> 这是整件事的分水岭。"log n 改不了"只统治比较世界。hash 能 O(1)，
> 不是因为它"更聪明"，而是因为它**换了个世界**，根本不在那棵决策树里。

---

## 2. 比较世界的铁底：log n 的数学证明

### 2.1 任何比较式算法都是一棵决策树

不管算法多巧（二分 / BST / 跳表 / 任意），只要**只靠比较**，执行过程一定是：

```
              x < a₃ ?
             /        \
          yes          no
          /              \
      x < a₁ ?         x < a₅ ?
      /     \          /     \
    叶子   叶子      叶子    叶子
```

- 每个**内部节点** = 一次比较（一个 yes/no）
- 每个**叶子** = 一个最终答案
- **某次查询做了多少次比较 = 根到叶子的路径长**
- **最坏比较次数 = 树高 h**

### 2.2 计数论证（数学核心）

在 n 个不同 key 里搜索，至少要能区分 **n+1 种答案**（等于第 1..n 个，或不在）。
不同答案必须落在**不同叶子**上（否则算法分不清 → 会答错），所以：

```
叶子数 L ≥ n+1
```

而二叉树（每次比较 2 个分支）高度 h 最多撑出 2^h 个叶子：

```
L ≤ 2^h
```

两式相夹：

```
2^h ≥ L ≥ n+1   ⟹   h ≥ log₂(n+1) = Ω(log n)
```

### 2.3 怎么理解这个铁底

> 20 个 yes/no 问题最多区分 2²⁰ ≈ 100 万样东西。
> 想区分 10 亿样，**无论问得多巧，至少问 30 次**（log₂10⁹ ≈ 30）。

- **有序数组 + 二分**：正好 ⌈log₂(n+1)⌉ 次 → **达到下界，最优**
- **平衡 BST**：Θ(log n) → 也最优
- **退化 BST（链）**：O(n) → 没把决策树建平衡，**白白浪费了树高**

> 补充：排序的 Ω(n log n) 是同一个论证，答案有 n! 种排列 → 叶子 ≥ n! → h ≥ log₂(n!) ≈ n log₂n。同一把尺子。

## 3. 树到底从哪冒出来的（解决"为什么搜索就是树"的卡点）

### 3.1 一次比较 = 一次分叉，"一连串分叉"的形状定义上就是树

靠比较搜索，本质是**一步步排除候选**，每个比较砍掉一半。把这个决策过程画出来，
**它本身就是一棵二叉树**。不是你选择用树，是"一串 yes/no"在数学上的名字就叫树。
**只要用比较搜索，你就已经在走一棵树了**，无论有没有意识到。

### 3.2 二分查找其实也是树，只是隐形的

```
有序数组: [1, 3, 4, 6, 7, 8, 10, 13, 14]   ← 没有指针，就是一排数

它二分时走的路：
         7         ← 中点
       /   \
      3     13
     / \    / \
    1   6  10  14
```

- **有序数组 + 二分** = 把这棵决策树**隐式**藏在下标计算里
- **BST** = 把同一棵树**显式**用节点 + 指针**摆出来**

→ 所以"为什么是树"的答案是：**它一直是树**，区别只在"算出来"还是"摆出来"。

### 3.3 那为什么要费劲摆出来（真建树）？—— 为了改得动

二分查找已经是树了，数组还更省内存，为什么发明 BST？
**唯一理由：插入/删除。**

```
有序数组插入 5：[1,3,4,6,7,...] → 6 后面全往后挪 → O(n) 💀
```

数组的"连续"是二分快的本钱，**也是改不动的诅咒**。
把树用指针摆出来后，插入只改几个指针，周围纹丝不动 → O(log n)。

> **树 = "比较式搜索"天生的树形，被指针 materialize 出来，**
> **好让它在保持有序的同时还能廉价增删。**

## 4. 内存世界的树：BST → 平衡 BST

### 4.1 BST 三件套

- **查找**：比 key 小往左，大往右，O(树高)
- **插入**：走到底挂上去
- **删除**：三种情况
  - 无孩子：直接删
  - 一个孩子：孩子顶替
  - 两个孩子：找**中序后继**（右子树一路向左到底）的值复制过来，再去右子树删那个后继（它最多一个右孩子，退化成前两种）

**死穴**：按顺序插入（自增 ID！）→ 退化成链 → 搜索掉回 O(n)。
→ 必须**强制平衡**。

### 4.2 平衡 BST（AVL / 红黑）：代价在修改，好处是搜索被保证快

平衡是**为了救搜索**（别退化成 O(n)），代价付在**修改**上：

```
普通 BST 插入:  走到底，挂上 → 完事            （便宜，但可能歪成链）
平衡 BST 插入:  走到底，挂上 → 发现歪了 → 旋转掰正  （多花力气换"搜索永不退化"）
```

**旋转**：只改几个指针，O(1)，且**不破坏中序有序性**（这是它能用的根本原因）。

```
      y                 x
     / \               / \
    x   C   右旋 →     A   y
   / \                    / \
  A   B                  B   C
```

> 一句话：**平衡树 = 每次修改多花点力气（旋转），来买"搜索永远快"的保证。**
> （不是"修改廉价、搜索慢"，是反过来。）

### 4.3 AVL vs 红黑：真正的"搜索快 ↔ 修改便宜"跷跷板

| | AVL | 红黑树 |
|---|---|---|
| 平衡卡得 | 严（左右高差 ≤ 1） | 松（最长路 ≤ 2×最短路） |
| 树更矮 → 搜索 | 更快 | 稍慢 |
| 越严 → 修改旋转越勤 | 修改更贵 | 修改更便宜 |
| 用在 | 读多写少 | 通用（map / 内核 / TreeMap） |

红黑树的 5 条颜色规则**不用背**：记住"它用染色+偶尔旋转把树高控制在 2 倍最优内"即可。要写的时候再查。

### 4.4 内存树的死穴（通往 B-Tree 的桥）

红黑树是**二叉**：n=10⁹ → 树高 log₂(10⁹) ≈ 30 层。
若这树在**磁盘**上，每下一层 = 一次随机 IO → 单查询最坏 30 次 IO 💀。
且每个红黑节点才几十字节，却要搬一整页 4KB → **浪费 4000+ 字节**。

→ 解法：既然一次必搬一页，**就把这页塞满 key** → 一个节点几百孩子 → 树瞬间变矮。
**这就是 B-Tree**：把红黑树压扁，让"一个节点 = 一个磁盘页"。

## 5. B-Tree：不是二分，但照样 log n

### 5.1 分清"层数"和"总比较次数"

| | 二叉平衡树 | B-Tree（每节点最多 B 孩子） |
|---|---|---|
| 层数（高度） | log₂n | **log_B n**（更少） |
| 每层比较 | 1 次 | 节点内 B 个 key 二分 → log₂B 次 |
| **总比较** | log₂n | log_B n × log₂B |

### 5.2 换底公式：乘出来还是 log₂n

```
log_B n × log₂B = (log₂n / log₂B) × log₂B = log₂n
```

用了换底 `log_B n = log₂n / log₂B`。这也是为什么写 O(log n) **从不写底数**——
换底只差常数因子，大 O 里被吸收，log₂n / log_B n / ln n 全是同一个 Θ(log n)。

### 5.3 代真数体感（n=10⁹, B=100）

```
层数:    log_100(10⁹) = 9/2 ≈ 4.5 层     （二叉要 30 层）
每层:    100 个 key 里二分 = log₂100 ≈ 6.6 次
─────────────────────────────────────────
总比较:  4.5 × 6.6 ≈ 30 次   ← 又回到 log₂(10⁹) ≈ 30
```

**层数从 30 砍到 4.5，但总比较纹丝不动。**

### 5.4 深意：铁底不许它作弊

砍了层数为什么总比较不变？因为 **§2 的 log₂n 铁底锁死了它**。
B-Tree 把层数压到 log_B n，就**必须**在每个胖节点里多比 log₂B 次还回来。
**省下的层数，一分不差在节点内部还回去了。**

```
二叉树:   30 次比较，摊在 30 个节点里（每节点 1 次）
B-Tree:   30 次比较，挤进 4.5 个节点里（每节点 ~6.6 次）
```

> **B-Tree 优化的不是比较次数（锁死了），是"比较被分装进多少个要摸的节点"。**
> 磁盘上摸一节点 = 一次贵 IO → 4.5 次 IO vs 30 次 IO → B-Tree 血赚。

## 6. 计算世界的 hash：凭什么 O(1)、代价是什么

hash **根本不问大小**，不在决策树里，§2 的铁底管不到它：

```
查 k:  i = hash(k)     ← 一次算术，直接算成下标
       看 table[i]      ← 一次数组访问
```

### 数学：为什么期望 O(1)

表大小 m，存了 n 个，**负载因子 α = n/m**。拉链法 + 均匀 hash：

```
每槽期望挂 α 个
一次查找 = 算 hash(1) + 扫链(期望 α) = 1 + α = Θ(1)   （α 是常数时）
```

只要满了就扩容 rehash 维持 α < 某常数，增删查**期望都 Θ(1)**。

### 三笔代价（取舍）

1. **丢掉顺序** 💀 最致命 —— hash 把 key 打散，相邻 key 离十万八千里 →
   不能范围查 / 不能前驱后继 / 不能找最小 / 不能有序遍历，只剩**点查**。
2. **最坏退化** —— 全撞一个槽 → O(n)。靠好 hash 兜住"期望"，但最坏仍 O(n)；
   树是**最坏 O(log n) 的硬保证**。
3. **空间换时间** —— α < 1 总有空槽浪费，扩容 rehash 要重算全部。

## 7. 全景表（理想扁平模型：每次操作记 1 单位，摸节点免费）

| 结构 | 世界 | 查找 | 插入 | 删除 | 有序？ |
|---|---|---|---|---|---|
| 无序数组 | 比较 | O(n) | O(1) 追加 | O(1) 换末尾 | ❌ |
| 有序数组 | 比较 | Θ(log n) **最优** | O(n) 挪 | O(n) 挪 | ✅ |
| BST（不平衡） | 比较 | 均摊 log n / 最坏 n | 同左 | 同左 | ✅ |
| 平衡 BST | 比较 | Θ(log n) **保证** | Θ(log n) | Θ(log n) | ✅ |
| B-Tree | 比较 | Θ(log n) | Θ(log n) 比较 + 节点内 O(B) 搬移 | 同左 | ✅ |
| 哈希表 | **计算** | Θ(1) 期望 | Θ(1) 期望 | Θ(1) 期望 | ❌ |

**注意 B-Tree 那行**：扁平模型下它的操作数和平衡 BST 一样，还多了"节点内搬移"和"半满浪费空间"。
→ **扁平模型里 B-Tree 是多余的复杂度**，它的全部价值寄生在"摸节点很贵且能批量拿"这条现实约束上（我们这次故意假设没了，所以它该消失）。

## 8. 收口：理想世界其实只剩两个赢家

```
需要"有序"吗？(范围查 / 前驱后继 / 最小值 / 有序遍历)
│
├─ 不需要，只点查  ──────────►  哈希表        Θ(1)      （计算世界，绕过铁底）
│
└─ 需要  ──►  进入比较世界，铁底 Θ(log n)
              │
              ├─ 数据静态  ──►  有序数组+二分   Θ(log n)，最简
              │
              └─ 数据动态  ──►  平衡 BST        Θ(log n)，三操作全保证
```

- **要顺序 → 被 log n 锁死**，最优是平衡 BST（动态）或有序数组（静态）
- **不要顺序 → 换到计算世界 O(1)**，但永远失去顺序

**选哪个，只取决于一个问题：摸一次节点相对比一次大小，贵多少？**
- 摸节点免费 → 红黑/AVL（最精简）
- 摸节点很贵且能批量拿（磁盘页 / cache line）→ B-Tree / B+Tree

## 9. 这套理论怎么落到 ch03

ch03 写 B+Tree 而不是把内存红黑树持久化，原因正是 §8 那条轴：
**数据在磁盘上，"摸一页"（page fault / IO）的成本 ≫ "比一次大小"。**

于是那条被理想模型假设掉的轴**重新出现并主导一切**，
B-Tree/B+Tree 从"多余的复杂度"变成"唯一正确的选择"。

而 ch02 做的 Pager（4KB 分页）正是为这个铺路：**B+Tree 的一个节点 = 一个 page**。
3.1 节点字节布局，本质就是"决定 4096 字节里怎么排几百个 key 和孩子指针"——
让"一次摸页"尽可能多塞 key，把树压到 3~4 层。

> B+Tree 相对 B-Tree 的额外优化（数据只放叶子 + 叶子链表）见 ch03 设计动机，
> 核心是为"范围扫描"和"更高扇出"服务，与本笔记的 log n 框架一脉相承。
